# 관리자 성능 측정

2026-10-05 사용자 요청의 1단계에서 원인 구분을 위한 시간을 측정했다. 아래 기준값은 최적화 전 결과이며, 후속 2단계 변경은 마지막 절에 구분해 기록한다.

## 측정 켜기

기본은 꺼짐이다. 로컬에서는 다음 명령으로 실행한다. `.env.local`을 수정할 필요가 없다.

```sh
ADMIN_TIMING=true NEXT_PUBLIC_ADMIN_TIMING=true npm run dev -- --hostname 127.0.0.1
```

- 서버 콘솔 `[admin-timing]`: Proxy 인증, 페이지 인증, 조회 API 인증·권한 확인·DB 요청 시간을 ms로 기록한다.
- 조회 API의 `Server-Timing`: 인증·DB 요청·핸들러 전체 시간이다. `handler`는 Proxy, Next.js 컴파일, 브라우저 전송 시간을 포함하지 않는다. 병렬 요청의 개별 시간은 더하지 않는다.
- 브라우저 콘솔 `[admin-browser-timing]`: 문서/RSC/API 응답 시간·TTFB·응답 크기와 메뉴 이동 시작부터 관리자 셸/주문 목록 React 반영까지의 시간이다. `orders_committed`는 React effect 시점이며 실제 디스플레이 페인트 시간이나 전체 화면 상호작용 준비 시간을 의미하지 않는다. 발송 관리의 출력 묶음은 별도 API이므로 주문 목록 반영 후에도 로딩 중일 수 있다.
- 고정된 메뉴·단계 이름, 무작위 측정 ID, 시간, HTTP 상태·응답 크기만 기록한다. 검색어, 주문번호, 사용자 ID, 주소, 전화번호, 쿠키, 키, 응답 본문을 기록하거나 외부 분석 서비스로 전송하지 않는다. 서버 내부 계측은 GET에만 적용한다. 브라우저 Resource Timing은 허용된 관리자 경로의 응답 시간만 관찰하며 GET/POST 메서드를 구분하지 않는다.
- 브라우저 계측 플래그는 빌드 시 반영된다. 프로덕션 빌드 비교 시 같은 플래그로 빌드하고 서버 계측 플래그로 실행해야 한다. 운영 배포의 계측 활성화 여부는 확인하지 않았다.

## 비교 방법

1. 관리자 로그인 후 카운터에 직접 진입하는 요청을 측정한다.
2. 카운터 → 주문 관리 → 발송 관리 → 상품·재고 → 설정 → 카운터를 이동하며 각 요청과 목록 반영 시간을 확인한다. 데이터 변경 버튼은 누르지 않는다.
3. 첫 요청과 반복 요청을 분리하고 반복 요청을 최소 5회 측정해 중앙값·범위를 비교한다. 개발 환경은 첫 컴파일·Fast Refresh·Strict Mode의 중복 effect 요청을 별도로 구분한다.
4. 동일 코드의 로컬 프로덕션 빌드와 비교한 뒤 운영 배포 환경을 확인한다. 로컬 프로덕션 빌드의 결과도 Vercel 성능으로 간주하지 않는다.
5. 서버 인증과 DB 요청, 화면/API 응답, 목록 반영 시간을 비교해 다음 개선을 선택한다. DB 요청 측정값에는 HTTP·네트워크·Supabase API·JSON 처리 등이 포함되므로 SQL 실행 시간으로 보고하지 않는다.

## 2026-10-05 예비 측정

개발 PC에서 현재 Supabase 프로젝트의 기존 조회 요청을 6회씩 실행했다. 서버용 클라이언트로 주문·상품·설정만 읽었고 관리자 인증·Next.js·브라우저 렌더링은 제외했다. 주문 조회는 기존 `list_checkouts` RPC의 첫 페이지, 상품은 기존 정렬 전체 목록, 설정은 배송·발송 설정의 병렬 조회다. 주문 본문과 개인정보는 저장하지 않았다.

| 항목 | 첫 요청 | 이후 5회 중앙값 | 이후 5회 범위 | 응답 크기(대략) |
| --- | ---: | ---: | ---: | ---: |
| 주문 목록 | 584ms | 202ms | 193–492ms | 12.8KB |
| 상품 목록 | 521ms | 191ms | 189–195ms | 2.6KB |
| 설정 2개 병렬 조회 | 522ms | 535ms | 204–540ms | 0.2KB |

원시 시간(ms, 첫 요청부터): 주문 `584,486,492,195,202,193`, 상품 `521,190,195,193,189,191`, 설정 `522,540,540,535,525,204`. 첫 요청은 이 측정 순서의 첫 샘플이라는 의미이며 Supabase 콜드 스타트를 확인했다는 뜻이 아니다.

상품의 작은 응답도 반복 조회에 약 190ms가 걸렸다. 순차 원격 요청이 여러 번 누적되는 구조를 확인할 필요가 있지만, 이 값만으로 네트워크 또는 DB가 주원인이라고 확정할 수 없다. 설정 요청 편차도 SQL 실행 시간 측정 없이 원인을 단정하지 않는다.

## 로그인 후 메뉴 이동 측정

사용자가 Aside 브라우저에 로그인한 뒤 실제 관리자 세션으로 측정했다. 동일 PC·Supabase 프로젝트에서 로컬 개발 서버와 동일 코드의 격리된 로컬 프로덕션 빌드(Webpack)를 순서대로 실행했다. 기존 브라우저의 iPad Mini 768×1024 에뮬레이션·네트워크 No throttling 설정을 유지했다. API 응답 본문이나 인증정보를 별도로 저장하지 않았고 조회만 수행했다.

아래는 카운터↔주문 관리 메뉴를 각각 5회 반복 이동한 결과다. 이동 시작부터 `orders_committed`까지이며 자동화 도구의 대기 시간은 포함하지 않는다. 두 환경을 동시에 교차 측정한 실험은 아니므로 개발/프로덕션 차이를 정밀한 개선율로 해석하지 않는다.

| 환경 | 메뉴 | 5회 중앙값 | 범위 |
| --- | --- | ---: | ---: |
| 로컬 개발 | 카운터 | 1,490.9ms | 1,384.8–1,956.7ms |
| 로컬 개발 | 주문 관리 | 1,789.0ms | 1,381.4–2,270.9ms |
| 로컬 프로덕션 | 카운터 | 1,556.7ms | 1,285.8–1,714.2ms |
| 로컬 프로덕션 | 주문 관리 | 1,449.9ms | 1,271.2–1,619.8ms |

반복 원시 시간(ms):

- 개발 카운터: `1937.9,1956.7,1384.8,1490.9,1398.7`
- 개발 주문 관리: `2270.9,1834.5,1520.9,1789,1381.4`
- 프로덕션 카운터: `1675.2,1539.9,1285.8,1556.7,1714.2`

개발 카운터의 첫 메뉴 이동 2,823.4ms는 준비 샘플로 제외했다. 주소 직접 진입은 개발 주문 관리 1,784.5ms, 프로덕션 카운터 2,136.4ms를 각각 한 번 관측했다. 서로 다른 경로의 단일 샘플로 직접 비교하지 않는다. 브라우저 Navigation Timing이 로드 완료 전에 내보낸 duration 0 기록도 응답 시간 집계에서 제외했다.

### 요청별 대기 구간

다음 API 통계는 위 5회 반복뿐 아니라 첫 진입과 다른 메뉴 확인을 포함한다. `DB 요청`은 서버에서 Supabase 응답을 기다린 시간으로 SQL 실행 시간과 다르다.

| 환경 | 요청 | 표본 수 | 브라우저 응답 중앙값 | DB 요청 중앙값 |
| --- | --- | ---: | ---: | ---: |
| 로컬 개발 | 주문 목록 API | 26 | 880.5ms | 211.4ms |
| 로컬 개발 | 상품 목록 API | 28 | 909.5ms | 200.4ms |
| 로컬 프로덕션 | 주문 목록 API | 12 | 797ms | 206.2ms |
| 로컬 프로덕션 | 상품 목록 API | 13 | 781ms | 203.4ms |

프로덕션 주문 API 한 요청의 예: 브라우저 응답 734ms 중 핸들러는 527.1ms였다. 내부는 `getUser` 161.6ms → `is_staff` 164.9ms → 주문 조회 199.1ms 순서다. 핸들러 이전 Proxy의 인증도 별도 요청이며, 주문 API 12회에서 중앙값 170.1ms였다. 주문 조회보다 인증·권한 확인을 위한 원격 왕복의 합이 더 컸다.

메뉴 이동은 페이지의 인증·권한 확인을 기다린 뒤 클라이언트가 API를 시작한다. 반복 10회에서 관리자 셸 반영 중앙값은 개발 585.4ms, 프로덕션 531.7ms였다. 이후 주문·상품 API 응답을 기다려 목록이 반영됐다. 관련 코드:

- `src/proxy.ts`: 페이지/API 요청마다 `getUser`.
- `src/features/admin/auth.ts`의 `getStaff`: `getUser` 후 `is_staff` RPC.
- `src/app/namu-admin/[section]/page.tsx`: `getStaff` 완료 후 `AdminShell` 반환. `key={section}`으로 메뉴 이동 시 다시 마운트.
- `src/features/admin/orders-admin.tsx`: 마운트 이후 주문·상품을 `Promise.all`로 조회하고 둘 다 끝나야 목록 표시.

프로덕션 카운터 마지막 반복에서는 주문 API가 737ms였지만 상품 API가 1,185ms여서 목록이 상품 조회를 약 448ms 더 기다렸다. 셸 반영은 525.1ms, 목록 반영은 1,714.2ms였다. 카운터·주문 목록의 기본 표시를 상품 조회와 분리할 여지가 있다.

개발에서는 마운트 effect가 두 번 실행되어 메뉴마다 주문·상품 API가 각각 2회 관측됐다. 기존 effect의 `live` 플래그는 오래된 결과 반영만 막고 요청을 취소하지 않는다. 프로덕션에서는 각각 1회였지만 1.3–1.7초 정도의 대기가 남았다. 개발 모드의 중복 요청만으로 전체 지연을 설명할 수 없다.

다른 메뉴는 한 번씩 확인했다. 프로덕션 발송 관리의 주문 목록 반영은 1,767.2ms였고 출력 묶음 API는 별도로 1,022ms가 걸렸다. 상품·설정·문자 내역은 셸 반영이 각각 521.4/529.6/515.8ms, 해당 API 응답이 717/761/736ms였다. 이 세 화면에는 최종 반영 마커가 없어 전체 표시 시간을 확정하지 않는다. 초기 viewport 프리페치 요청도 Proxy를 통과했지만 메뉴 클릭 시간과 분리했다.

### 다음 개선 우선순위와 한계

1. 서버·DB 권한 검사를 유지하면서 반복되는 원격 인증·권한 조회를 줄일 수 있는지 검토한다. 인증 결과를 사용자 간 공유 캐시로 바꾸거나 검사 자체를 생략하지 않는다.
2. 페이지 인증 완료 → 클라이언트 마운트 → API 조회의 순차 대기를 줄이고, 주문 목록을 상품 조회 완료와 분리한다.
3. 메뉴 재방문 시 재조회 범위와 캐시 무효화 방식을 정한다. TanStack Query 도입은 확정 사항이 아니며 이번 단계에서 추가하지 않았다.

현재 측정은 **로컬 서버에서 실제 Supabase를 조회한 결과**다. 운영 Vercel 서버의 리전·콜드 스타트·네트워크 경로와 운영 관리자 화면은 아직 실측하지 않았다. SQL 실행 계획, DB 내부 실행 시간, 리전 간 지연도 확인하지 않았으므로 Supabase DB 자체가 느리다고 단정하지 않는다. 최초 비로그인 접속의 만료 토큰 오류는 정상 로그인 후 반복 지연의 원인으로 사용하지 않았다. 다음 변경 후 같은 조건으로 재측정해야 실제 개선 폭을 판단할 수 있다.

검증: 타입 검사·변경 파일 린트, 단위 테스트 29개, 격리 디렉터리의 프로덕션 빌드 통과. 계측을 켠 상태에서도 비로그인 주문·상품·설정 API는 모두 401이고 데이터를 반환하지 않는다. 단위 테스트에서 계측 비활성 시 로그/헤더 부재, 반환값·예외 유지, 민감한 결과/오류 본문 비기록을 확인했다.

## 2단계: 인증 왕복과 목록 대기 분리

사용자 요청에 따라 기존 미커밋 변경을 `32c153f`로 커밋하고 `origin/main`에 푸시한 뒤 아래 개선을 진행했다. DB 마이그레이션, TanStack Query 도입, SSR 초기 주문 조회, 주문 데이터 캐시는 이번 단계에 포함하지 않는다.

- 관리자 경로의 Proxy는 `getUser()` 대신 `getClaims()`로 토큰을 검증·갱신한다. 실제 프로젝트의 공개 JWKS에서 ES256 키를 확인했다(공개 키 존재가 모든 기존 세션의 서명 방식을 보장하지는 않는다). 비대칭 키의 공개 키 캐시가 준비되면 Auth 사용자 조회 왕복을 줄이며, 구형 대칭 키 세션에는 SDK의 서버 검증 대체 경로가 적용된다. 고객 경로의 기존 Proxy 처리는 유지한다.
- `getStaff()`의 실제 사용자 확인(`getUser`)과 DB 관리자 확인(`is_staff`)은 페이지·조회/변경 API에서 그대로 수행한다. 토큰이 유효하다는 이유만으로 관리자 접근을 허용하지 않는다. 인증 결과의 사용자 간 공유 캐시를 추가하지 않는다. Supabase SSR의 [토큰 검증·갱신 안내](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs)를 기준으로 한다.
- `OrdersAdmin`은 주문이 도착하는 즉시 목록을 표시한다. 상품 필터 요청은 별도 오류·재시도 상태를 가지며 검색·페이지 이동마다 상품을 다시 가져오지 않는다. 명시적 새로고침/처리 후 갱신에는 상품 필터도 갱신한다. 카운터 첫 로딩은 주문만 조회한다.
- `ReorderEditor`는 열릴 때 최신 상품과 설정을 병렬로 조회한다. 두 조회가 성공해야 편집 폼을 표시하며 실패 시 다시 불러오기/목록 복귀를 제공한다. 이미 전송한 재접수의 결과 확인은 기존 저장 요청을 그대로 사용한다. 목록·상품·재접수 조회는 해당 화면을 떠나면 브라우저 요청을 중단하고 늦은 응답을 반영하지 않는다. 서버에서 이미 시작된 작업까지 취소된다고 가정하지 않는다.
- `(workspace)` 공통 레이아웃에 정적인 메뉴를 유지하고 `[section]/loading.tsx`에서 인증 대기 중 로딩 표시를 제공한다. 메뉴 링크에는 이동 대기 표시를 제공한다. 로그인·인쇄 화면은 이 레이아웃을 사용하지 않으며, 실제 데이터는 기존과 같이 페이지/API에서 권한 확인 후 제공한다.
- 기존 `shell` 계측 지점은 공통 레이아웃 표시 시점으로 앞당기지 않고, `AdminSectionContent`의 페이지 인증 완료 후 effect에 유지했다. 따라서 기준 측정과 같은 의미로 비교한다. 코드 경로는 `src/app/namu-admin/(workspace)/[section]/page.tsx`로 이동했으며 URL은 동일하다.

### 2단계 검증 결과

- 타입 검사·전체 린트·단위 테스트 29개·격리된 Webpack 프로덕션 빌드 통과.
- 기존 관리자/회원 권한·주문/재접수·결제·취소·인쇄 39개와 새 성능/인증 시나리오 24개, 총 63개 브라우저 검증이 최종 통과했다(데스크톱·태블릿·모바일 각각 실행한 수 포함). 실제 마이그레이션을 적용한 격리 PGlite와 테스트 전용 인증 서버를 사용했다. 원격 주문·문자·계정은 변경하지 않았다.
- 새 인증 대역은 ES256으로 실제 서명하고 공개 JWKS를 제공한다. 관리자 API 한 요청에서 Auth 사용자 조회가 1회인 것을 확인했다. 유효기간이 지난 토큰의 갱신·쿠키 반영, 구형 HS256 대체 경로, 토큰 서명은 유효해도 사용자 조회가 거절되거나 관리자 역할이 제거된 경우의 조회/변경/페이지 접근 차단을 확인했다.
- 상품 응답을 의도적으로 지연·실패시켜도 주문 목록이 보이고 상품 필터 재시도·검색이 동작하는지 확인했다. 카운터 진입의 상품 요청 0회, 재접수 진입 시 조회·실패 후 목록 복귀/재시도, 메뉴 DOM 유지·이동 대기 표시·가로 넘침을 확인했다. 태블릿·모바일 캡처도 시각 검토했다.
- 신규 테스트의 출처 헤더 누락으로 403이 발생했고, 상품 선택자 및 Next 라우트 알림과의 중복 선택을 보완했다. 해당 시나리오는 수정 후 모두 재실행해 통과했다. 앱의 출처 검사를 완화하지 않았다. 최종 재접수/오류 처리 변경 후 기존 주문 업무 시나리오도 3개 화면 크기에서 다시 통과했다.

### 로그인 후 개선 결과 재측정

사용자 재로그인 후 같은 PC·Aside·iPad Mini 768×1024·No throttling 조건에서 실제 Supabase 조회를 다시 측정했다. 로컬 개발 서버와 최종 개선 코드가 동일한 격리 프로덕션 빌드(포트 3121)를 사용했다. 다음 표는 메뉴 이동부터 `orders_committed`까지이며 첫 준비 이동은 제외했다.

| 환경 | 메뉴 | 개선 전 5회 중앙값 | 개선 후 표본 수 | 개선 후 중앙값 | 개선 후 범위 |
| --- | --- | ---: | ---: | ---: | ---: |
| 로컬 개발 | 카운터 | 1,490.9ms | 5 | 1,567.6ms | 961.5–1,618.5ms |
| 로컬 개발 | 주문 관리 | 1,789.0ms | 5 | 1,638.3ms | 1,328.6–2,207.7ms |

개발 모드에서는 주문 관리 중앙값이 줄었지만 카운터 중앙값은 늘었다. 측정 시점이 다른 소수 표본이며 원격 요청 편차도 커서 전체 화면이 일관되게 빨라졌다고 결론 내리지 않는다. 이번 반복 10회의 주문 API 응답 중앙값은 871.5ms, 내부 DB 요청 중앙값은 498.4ms였다. DB 요청은 190.2–621.9ms로 변동했으며 SQL 실행 시간만을 뜻하지 않는다. 이전 측정과 요청 표본 범위도 다르다.

개발 반복 원시 시간(ms):

- 카운터: `1297.7,1618.5,1567.6,1611.5,961.5`
- 주문 관리: `1328.6,1774.9,1638.3,1437.1,2207.7`
- 제외한 준비 이동: 주문 관리 `3389`(첫 컴파일 포함), 카운터 `1271.7`.

프로덕션은 준비 이동 후 **메뉴별 1회만 유효하게 수집**했다. 카운터 `945.9ms`, 주문 관리 `1280.4ms`였으며 5회 반복 비교는 미완료다. 준비 이동은 카운터 `954.3ms`, 주문 관리 `1024.7ms`로 별도 구분한다. 최초 주소 직접 진입의 카운터는 `1493.6ms`(페이지 인증 완료 후 셸 `844.1ms`)였지만 단일 샘플이다. 이 값들을 이전 5회 중앙값과 같은 통계로 비교하거나 개선율로 표시하지 않는다.

구조 변경의 실제 동작은 다음과 같이 확인했다.

- 카운터 진입 시 상품 API 요청은 0회였다. 주문 관리에서는 상품 필터만 별도 조회했다.
- 개발 주문 관리 첫 반복에서 주문 API `867ms`, 상품 API `1234ms`였고 목록은 메뉴 이동 후 `1328.6ms`에 반영됐다. 늦은 상품 응답까지 목록을 기다리지 않았다. 프로덕션 준비 이동에서도 주문 API `578ms`, 상품 API `882ms`로 같은 분리를 확인했다.
- 프로덕션의 최초 진입·준비 이동·유효 반복에 해당하는 주문 API 5회의 Proxy 단계 중앙값은 `2.1ms`(범위 `0.6–5.4ms`)였다. 개선 전 12회 중앙값 `170.1ms`와 표본 범위는 다르지만 중복 원격 인증 왕복이 줄어든 방향을 확인했다. 페이지/API의 실제 사용자·관리자 검사 비용은 여전히 남아 있다.
- 개발 Strict Mode에서 중단된 선행 요청은 응답 본문 크기 0·서버 계측 부재로 구분해 완료된 API 통계에서 제외했다. 초기 Navigation Timing의 duration 0 기록도 제외했다.

**측정 한계:** 프로덕션 추가 반복 도중 UI 자동화가 `noWindowsAvailable` 및 클립보드 읽기 시간 초과로 실패했다. 이후 조작 시도의 로그는 유효 표본에 넣지 않았다. 로그인 자체는 확인했으나 창 조작 복구가 필요해 사용자에게 Aside 창을 화면에 띄워 달라고 요청했다. 운영 Vercel 실측도 수행하지 않았다. 이후 사용자가 성능 개선은 현재 단계까지만 진행하고 다른 수정으로 전환하기로 결정했으므로, 이 미완료 측정은 한계로 남긴다.

2단계 개선은 구현·측정 당시 사용자 지시에 따라 미커밋 상태로 보관했다. 이후 사용자가 현재까지 작업의 커밋·푸시를 요청하여 배송 문구 정리와 함께 반영한다. SSR 초기 조회·재조회 축소·브라우저 캐시는 후속 제안이며 구현하지 않았다. 추가 성능 작업은 사용자가 다시 요청할 때 진행한다.
