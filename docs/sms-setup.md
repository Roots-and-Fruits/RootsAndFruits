# SOLAPI 주문 문자 설정

주문접수·발송 안내 모두 **주문에 입력된 보내는 분 휴대폰**으로 보낸다. 로그인 회원의 프로필 번호나 받는 분 번호를 사용하지 않는다. 알리고 계정은 필요하지 않다.

## 먼저 준비할 것

1. [SOLAPI](https://solapi.com/) 가입·계정 인증을 완료한다.
2. 사용할 발신번호를 등록·인증하고 발송 잔액을 충전한다.
3. 콘솔에서 API Key와 API Secret을 발급한다. 키는 코드·대화·스크린샷에 올리지 않는다.
4. Supabase SQL Editor에서 `supabase/migrations/202610030001_order_notifications.sql`을 실행한다. 기존 주문은 변경하지 않으며 문자 기능은 꺼진 상태로 생성된다.
5. 로컬 `.env.local` 및 실제 운영할 Vercel **Production 환경**에 아래 서버 환경변수를 설정한다. Preview 환경에는 실제 발송을 켜지 않는다.

```dotenv
SMS_ENABLED=true
SOLAPI_API_KEY=발급받은_키
SOLAPI_API_SECRET=발급받은_시크릿
SOLAPI_SENDER_NUMBER=등록한_발신번호_숫자만
```

6. 로컬 서버 재시작 또는 Vercel 재배포 후 관리자 `/namu-admin/notifications`의 **문자 켜기**를 선택한다.
7. 본인 번호로 새 주문을 접수하고 수신을 확인한다. 발송 안내는 결제 → 엑셀 출력 → 발송 완료 처리 후 별도로 확인한다. 이 과정은 유료 실발송이며 자동으로 수행하지 않았다.

`SMS_ENABLED=false`는 해당 실행 환경에서 외부 발송을 막는다. 관리자 **문자 끄기**는 DB 전체의 신규 알림 생성을 중지하고 아직 대기 중인 건을 발송 제외 처리한다. 이미 전송 중인 문자는 취소하지 못한다. 재활성화해도 과거 접수·발송 건은 소급 생성하지 않는다. 같은 DB를 쓰는 로컬·운영 환경은 관리자 켜짐 설정을 공유하므로 로컬의 `SMS_ENABLED`는 실발송 시험 때만 켠다.

## 발송 시점과 문구

- 접수: 결제 전 주문 접수 성공 시 결제주문당 1회. 배송지가 여러 개여도 1회이며 관리자 재접수는 새 주문이므로 새 안내를 보낸다.
- 발송: 배송지별 실제 `발송 완료` 전환 시 1회. 엑셀 출력만으로는 발송하지 않는다. 여러 배송지를 서로 다른 날짜에 보내면 각각 보낸다.
- 받는 분에게는 보내지 않는다. 마케팅 선택 동의와 무관한 주문 안내이며 광고 문구를 포함하지 않는다.
- 문구 파일: `src/features/notifications/messages.ts`. 이름·주소 전체나 송장번호를 접수 문자에 담지 않는다. 발송 문자는 주문번호·배송지 순번·수령인 이름으로 구분한다. 송장 업로드/택배사 API는 새로 추가하지 않았다.
- 길이에 따라 SOLAPI가 SMS/LMS를 판정한다. 현재 안내 문구는 대체로 **장문 LMS**로 처리되므로 LMS 요금 기준으로 준비한다. 최신 요금은 [공식 요금표](https://solapi.com/pricing)를 확인한다.

## 발송 내역과 재처리

주문과 알림 작업을 같은 DB 트랜잭션으로 저장하고 주문 응답 후 발송한다. 접수 요청 재시도·발송 완료 버튼 반복으로 같은 안내가 생성되지 않으며 DB에서 작업을 선점해 중복 요청을 막는다. SOLAPI 장애가 주문 접수·결제·출고 자체를 실패시키지 않는다.

관리자 **문자 내역**에서 상태를 확인한다.

| 상태 | 의미와 조치 |
| --- | --- |
| 발송 대기 | 외부 발송 전. 대기 문자 보내기로 처리 가능 |
| 처리 중 | 서버가 선점해 요청 중 |
| 솔라피 접수 완료 | 공급자가 접수를 확인함. 휴대폰 수신 완료를 의미하지 않음 |
| 접수 실패 | 명확한 거절·잘못된 번호 등. 원인 해결 후 재시도 가능 |
| 결과 확인 필요 | 시간 초과·통신 단절·응답 이상. 이미 발송됐을 수 있어 자동/버튼 재시도하지 않음 |
| 발송 제외 | 보내기 전 주문 취소 또는 관리자 문자 끄기 |

최종 수신 성공·통신사 실패는 SOLAPI 콘솔에서 조회한다. 웹훅을 통한 수신결과 동기화는 포함하지 않았다. 조회 번호는 SOLAPI 그룹 ID이며 요청의 `customFields.notificationId`로 앱 내 알림 ID도 전달한다. `SOLAPI_숫자` 오류는 공급자 접수 거절 코드다. 원문 오류·키·메시지를 서버 로그에 남기지 않는다.

시간 초과 뒤에는 자동 재시도하지 않는다. 결과 저장 전 서버가 종료된 작업은 5분 후 다음 처리에서 `결과 확인 필요`로 바뀐다. 이 경우 콘솔에서 실제 전송 여부부터 확인한다. 관리자가 원래 주문을 다시 접수해 문자만 재발송하는 용도로 사용하지 않는다.

## 대기 작업 자동 복구

정상 주문·발송 요청 뒤 Next.js `after`로 즉시 처리한다. 처리 시간은 실행당 약 35~45초로 제한하며 대량 발송의 남은 작업·서버 중단으로 남은 작업은 DB에 보관한다. **정기 처리를 설정하지 않으면** 다음 주문/발송 요청 또는 관리자 `대기 문자 보내기`가 추가 처리를 시작한다.

운영에서 사용자 조작 없이 복구하려면 외부 스케줄러에 아래 요청을 1분 간격으로 등록한다. 스케줄러는 이번 코드 변경으로 자동 생성되지 않는다. 사용하는 플랫폼 요금제의 주기 제한을 확인한다.

- 서버 환경변수 `NOTIFICATION_CRON_SECRET`: 충분히 긴 임의 비밀값.
- 요청: `GET https://www.2180.co.kr/api/notifications/process`
- 헤더: `Authorization: Bearer <NOTIFICATION_CRON_SECRET>`
- 같은 실행이 겹쳐도 이미 선점한 알림은 다시 발송하지 않는다.
- 401: 인증값 오류, 503: 문자 환경 설정 또는 처리 실패. 키를 URL 쿼리에 넣지 않는다.

## 향후 알리고 알림톡 전환

`messages.ts`는 주문 안내, `dispatch.ts`는 작업 처리, `solapi.ts`는 공급자 통신, `server.ts`는 서버 환경/DB 연결을 담당한다. 이후 알리고 채널·승인 템플릿을 준비하면 공급자 어댑터와 템플릿 매핑을 추가한다. 현재 알리고 알림톡 전환 자체는 구현하지 않았다.

참고: [SOLAPI 발송 API](https://solapi.com/developers/api/messages), [공식 SDK 인증 구현](https://github.com/solapi/solapi-nodejs/blob/master/src/lib/authenticator.ts), [발신번호 등록](https://solapi.com/guides/senderid).
