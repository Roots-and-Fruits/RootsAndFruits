- 발송관리 목록·공통 주문 상세에서 번호를 확인할 수 있다. 저장 후 정상 매핑된 발송 대기 배송지에 한해 발송 완료 여부를 묻고 기존 날짜 경고·문자 설정을 유지한다. 번호 저장/교체만으로 문자나 발송 상태를 바꾸지 않는다. 이미 발송된 번호 수정도 안내를 재발송하지 않는다. 발송 실패 후 재시도와 저장 응답 유실 후 창 닫기 시 목록 갱신을 확인했다.
- `202610050002_delivery_tracking.sql`을 제공했다. 원격 SQL은 실행하지 않았으며 사용자가 기존 마이그레이션 다음에 직접 실행해야 한다. 기존 주문·상품·출력 파일·번호 시퀀스·문자 내역은 보존한다. 접수 당시 ID가 비어 있는 기존 택배사 파일을 이름·주소로 추측해 연결하지 않는다.
- 검증: 타입 검사, 전체 린트, 격리된 Webpack 프로덕션 빌드, 단위·PGlite DB 테스트 50개 통과. 배송 작업 목록+송장 업로드 브라우저 15개가 데스크톱·태블릿·모바일에서 통과했다. 최종 서버 날짜 연결 후 송장 테스트 6개를 재검증했고, 응답 유실 후 닫기 보완은 해당 브라우저 시나리오 1개와 타입/변경 파일 린트로 추가 확인했다. 세 화면 크기의 미리보기·교체·발송 확인 캡처를 시각 점검했다.
- 테스트 초기 로컬 포트 실행 제한·로그인 실패가 있어 실행 권한을 확보한 격리 서버로 재검증했다. 임시 오류 진단 코드는 제거했다. 실제 Supabase·문자 발송·환경값은 변경하지 않았고 커밋·푸시는 하지 않았다.

## 현재 상태: 관리자·비회원 연동 및 고객·태블릿 인증 코드

관리자 인증·상품·설정·카운터·결제 전 취소·재접수·엑셀·발송 처리와 비회원 접수 코드를 구현했습니다. 카카오·태블릿 인증 및 주문 회원 연결 코드도 추가했습니다. 원격 SQL과 Kakao provider 설정은 사용자가 설정 안내에 따라 적용하며, 아래 외부 연결 검증 기록과 구분합니다.
Supabase 원격 프로젝트의 연결값 설정 후 읽기 전용 연결 점검을 완료했습니다. 업무 테이블 10개의 조회, 공개 상품·배송 설정 조회, 관리자 조회 함수와 등록된 관리자 1명의 Auth 계정 존재를 확인했습니다. 비회원의 주문·배송·발송지 설정 조회 및 관리자 조회 함수 호출은 권한 오류로 차단됩니다.

연결 점검 시점에는 상품·주문이 0건이며, 공통 할인 0원·예약 최대 14일·송장 발송지 미입력 상태입니다. 상품 등록 후 실제 주문 접수 테스트가 필요합니다. 관리자 비밀번호 로그인·세션 갱신과 원격 DB 쓰기 흐름은 이번 읽기 전용 점검에서 검증하지 않았습니다. 아래 자동화 테스트 결과는 격리된 로컬 환경 기준입니다.

### 구현한 내용

- 관리자 2명만 ID·비밀번호로 접근하도록 Supabase Auth와 비공개 ID 매핑을 구성했습니다. 페이지·API에서 검증하고 DB 읽기는 RLS, 쓰기 함수는 service role 및 관리자 검증으로 제한합니다. 세션 갱신용 proxy를 연결했습니다.
- SQL에 결제주문·배송주문·당시 상품·금액·할인, 실제 재고 차감/반환·수동 조정 이력, 관리자 처리 이력, 출력 묶음·구성 배송지·파일 원본을 저장합니다. 원본 주문 내용은 수정 API로 노출하지 않습니다.
- 배송지별 할인 대상 상품을 합산해 2개마다 공통 금액을 할인합니다. 비대상 상품에는 할인하지 않고 할인액은 대상 상품 소계를 넘지 않습니다. 프런트 표시와 서버 접수 계산을 함께 변경했습니다.
- 접수는 서버의 현재 상품·설정으로 계산합니다. 주문번호 발급·주문 저장·재고 차감은 단일 DB 트랜잭션입니다. 같은 요청은 같은 번호와 금액을 반환합니다. 선택 이후 재고 부족을 이유로 고객 접수를 거절하지 않습니다.
- 접수 응답이 끊기면 원래 요청을 그대로 재확인합니다. 해결되지 않은 고객 요청이 있으면 새 주문 작성보다 접수 결과 확인을 먼저 제공합니다. 접수 성공 후 초안을 제거하고 최소한의 번호·금액만 완료 화면에 표시합니다.
- 브라우저 저장소를 사용할 수 없으면 같은 페이지 내 요청·완료 결과를 메모리로 유지합니다. 이 경우 새로고침을 통한 복구를 보장하지 않으며 완료 화면에서 번호 기록과 남은 공용 기기 입력 확인을 안내합니다.
- 카운터는 상품 식별자별 합산·할인·최종 금액을 보여주며 실제 POS 결제 후 기록합니다. 결제 완료·취소·엑셀 출력 확정은 주문 행 잠금으로 직렬화합니다. 최신 사용자 결정에 따라 취소는 결제 여부와 관계없이 모든 배송지가 엑셀 출력 전일 때 가능하며 실제 차감 기록만 한 번 반환합니다.
- 재접수는 전체 원본을 통합 수정 화면으로 가져오고 배송지 추가·제거도 가능합니다. 사용 불가 상품과 지난 예약일을 수정해야 하며 새 번호로 접수합니다. 원본·결제 상태를 변경하지 않습니다.
- 주문번호·송수신인·접수일·출발일·상품·결제/발송 상태 검색과 페이지 처리를 DB에서 수행합니다. 운영 메모는 배송주문별로 별도 저장합니다.
- 송장 엑셀은 기존 열 순서·문자열 값을 보존하며 실제 상품 수량을 사용합니다. 파일 생성 후 상태를 기록하며 중복 출력은 DB에서 차단합니다. 출력 이력에서 포함 주문·처리자·일시, 동일 파일 재다운로드, 묶음/선택 발송 처리를 제공합니다.
- 상품 삭제는 숨김이며 재고 관리와 할인 대상은 기본 끔입니다. 상품 정렬, 판매 여부, 수량 조정, 공통 할인·예약 기간·송장 발송지 설정을 관리합니다.
- 일반상품 등록·수정의 중량은 kg 단위로 입력하고 저장할 때 정수 g으로 변환합니다. 체험상품은 과일·중량·재고·할인을 사용하지 않습니다. 재고 수량 입력은 재고 관리 선택 시에만 표시하며 해제 시 입력 중인 조정값을 버리고 기존 수량을 보존합니다. 새 상품은 판매 중이 기본 선택입니다.
- 상품 목록을 일반·체험별 일렬 리스트로 변경했습니다. 일반상품은 dnd-kit 손잡이로 과일 그룹 및 같은 과일 안 상품을 이동하고, 체험상품은 그룹 없이 상품만 이동합니다. 순서 저장·취소를 제공합니다. 위·아래 이동 버튼과 숫자 순서 입력은 없습니다. 새 일반상품은 기존 그룹 끝 또는 새 그룹으로 목록 끝에 배치하고, 체험상품은 목록 끝에 배치합니다.
- `202609260002_product_order.sql`은 정렬 일괄 저장·재시도, 목록 변경 충돌 검사, 상품 수정 시 기존 순서 보존을 추가합니다. 해당 SQL은 로컬 테스트 DB에서 검증했으며 사용자가 Supabase SQL Editor 실행 결과(`normalize_product_order: NULL`)를 공유했습니다. 반환형이 void이므로 NULL 출력 자체는 정상입니다. 원격 함수 적용 상태를 별도로 조회한 것은 아닙니다.
- 관리자 전용 입력·선택·버튼 컴포넌트는 데스크톱(1024px 이상)에서 높이 36px, 작은 화면에서 최소 44px를 사용합니다. 데스크톱 메뉴는 한 줄, 상품 폼은 3열, 주문 검색은 4열, 설정은 기능별 2열로 배치하고 목록 간격을 줄였습니다. 고객 주문 화면의 공통 컴포넌트는 변경하지 않았으며 재접수 입력 크기는 관리자 영역에서만 조정합니다.

### 예약 배송 공통 datepicker

- React DayPicker(`@daypicker/react` 10)와 기존 Radix Dialog를 조합한 `src/components/forms/date-picker.tsx`를 추가했습니다. 날짜 선택 버튼에는 빈 값 안내 또는 한국어 날짜·요일을 표시하고 모달에서 한 달씩 탐색합니다. 모바일에서 7개 요일 열이 화면 너비를 넘지 않도록 달력 너비를 조정했습니다.
- 일요일·오늘+3일 이전·관리자 설정 기간 이후를 비활성화합니다. 화면에서만 막는 것에 그치지 않고 기존 단계/수정 폼/DB 검증도 유지합니다. 일반 배송과 체험의 날짜 계산은 변경하지 않았습니다.
- `DeliveryDateStep`을 통해 고객 주문·통합 수정·관리자 재접수에 공통 적용합니다. 날짜 선택 시 반영 후 닫고 닫기/Esc는 기존 값을 유지하며 포커스를 원래 버튼으로 돌립니다. 지난 예약일은 기존 값을 표시하며 재선택을 안내합니다.
- 날짜는 `src/lib/date-only.ts`로 로컬 달력의 연·월·일을 직접 변환해 저장 형식 `YYYY-MM-DD`를 유지합니다. UTC 변환으로 날짜가 달라지지 않도록 합니다.
- 구현 근거: [React DayPicker 설치](https://daypicker.dev/start), [날짜 비활성화](https://daypicker.dev/selections/disabling-dates), [달력 모달](https://daypicker.dev/guides/input-fields).

- 검증: 날짜 전용 값의 시간대·윤년 검증을 포함한 단위 테스트 14개, 타입 검사·린트·Webpack 프로덕션 빌드 통과. Chromium 세 화면 크기에서 예약 달력 제한·통합 수정·날짜 복원 9개, WebKit 26.6의 390px·320px 및 미국 시간대에서 같은 시나리오 6개를 확인했습니다. WebKit에서는 테스트의 연속 페이지 이동을 앞선 이동 완료 후 수행하도록 수정했습니다. 초기화된 격리 DB에서 예약 날짜를 고른 관리자 재접수와 결제·엑셀·발송 시나리오 3개도 통과했습니다. 실제 iPhone/iPad 하드웨어에서는 아직 확인하지 않았고 실제 Supabase 데이터는 변경하지 않았습니다.

### 상품 선택 목록 간격 조정

- 상품 행의 상하 여백과 그룹 간격을 줄이고 상품 정보·수량 조절을 좌우로 배치했습니다. 후속 피드백에 따라 줄바꿈 없는 flex 행으로 명시하고 상품 정보는 남은 너비, 수량 조절은 내용만큼의 고정 너비를 사용하도록 변경했습니다. 가격과 묶음 할인 배지를 같은 줄에 놓고 긴 설명은 줄바꿈합니다. 수량 버튼은 44px 터치 영역을 유지합니다. 공통 `ProductStep`을 사용하는 고객 주문·수정·관리자 재접수에 함께 적용됩니다.
- 데스크톱·태블릿·휴대폰의 짧은 설명 테스트 상품은 행 높이 66px이며 가로 넘침이 없었습니다. 기존 여러 배송지 상품 선택·합산·통합 수정 브라우저 테스트 3개와 타입 검사·린트·Webpack 빌드가 통과했습니다. 실제 iOS Safari에서는 검증하지 않았습니다.
- 후속 요청으로 예약 배송일은 아래 공통 datepicker로 교체했습니다.

### 관리자 재접수 하단 여백

- 재접수 화면은 고객 주문 페이지와 다른 바깥 레이아웃을 사용하므로 고정 액션 바의 높이만큼 하단 여백이 확보되지 않았습니다.
- `src/features/admin/reorder-editor.tsx`에 기존 `OrderActionBar`가 측정하는 `--order-action-height` + 1rem을 하단 여백으로 적용했습니다. 푸터의 실제 높이와 안전 영역 여백이 반영되며 배송지 추가 버튼까지 스크롤할 수 있습니다.

- 배송지 제거 직후 감시 중인 값 배열이 이전 길이를 잠깐 유지할 때 제거된 상품 필드를 그리던 오류도 수정했습니다. 편집 섹션은 `useFieldArray`의 현재 항목과 안정적인 ID를 기준으로 렌더링하고 상품 필드의 초기값을 명시합니다.

- 검증: 타입 검사·린트 통과. 기본 Turbopack 빌드는 포트 생성 권한 오류로 중단되어 `npm run build -- --webpack`으로 빌드 성공을 확인했습니다. 데스크톱·태블릿·휴대폰 관리자 시나리오 3개에서 페이지 끝의 배송지 추가 버튼이 푸터 위에 놓이는지, 실제 추가·제거 후 기존 상품과 금액을 유지해 재접수되는지 확인했습니다. 테스트용 임시 진단 로그는 제거했습니다.

### 관리자 주문 목록 배치 변경

- `src/features/admin/order-lists.tsx`로 목록 표시를 분리했습니다. 카운터·주문 관리는 결제주문당 한 행, 발송 관리는 배송지당 한 행을 사용합니다. 데스크톱에서는 열 제목과 내용을 맞추고 작은 화면에서는 한 행의 내용을 여러 줄로 배치합니다.
- 주문번호·한국 시간 접수 시각·보내는 분·배송지 수·결제금액·결제 상태를 표시하고 주문 관리에는 발송 상태별 배송지 건수를 요약합니다. 발송 목록은 선택·수령인·상품 수량·주소·메모·출발일·상태·상세 버튼을 유지합니다.
- 정렬은 기존 `list_checkouts`의 주문번호 내림차순을 유지합니다. 검색·페이지 처리·상세 모달·결제·재접수·엑셀·발송 API와 DB는 변경하지 않았습니다.

- 검증: 타입 검사·린트·빌드 통과. 로컬 테스트 통신 권한을 확보한 뒤 데스크톱·태블릿·휴대폰의 관리자 업무 시나리오 3개가 통과했습니다. 최신 주문 우선·행의 세로 배치·가로 넘침 방지·상세 조회·결제·엑셀·발송·재접수를 확인하고 화면 캡처를 검토했습니다. 실제 Supabase 데이터는 변경하지 않았습니다.

### HTTP 개발 환경의 주문 접수 오류 수정

- `SubmitOrder`가 API 호출 전에 `crypto.randomUUID()`를 직접 호출해, 해당 함수가 없는 브라우저에서 접수가 중단됐습니다. HTTP 내부망 접속에서는 이 API가 제공되지 않을 수 있습니다.
- `src/lib/request-id.ts`의 `createRequestId`를 주문 접수·관리자 재접수·엑셀 출력에서 공통 사용합니다. 네이티브 UUID API가 없으면 `crypto.getRandomValues`로 UUID v4를 생성하고 기존 요청 저장·재시도 방식을 유지합니다. 임의 시간값이나 `Math.random`으로 대체하지 않습니다.
- 실제 미확정 요청이 남아 있을 때만 같은 요청으로 재시도한다는 안내를 표시합니다. 요청 생성 전 오류에 접수 결과 확인 안내를 붙이지 않습니다.
- 요청 흐름은 브라우저 `POST /api/orders` → Next.js Route Handler → Supabase `submit_checkout` RPC입니다. 브라우저 개발자 도구에는 첫 구간이 표시됩니다. 예외는 화면 메시지로 처리하며 주문 내용·개인정보를 콘솔에 기록하지 않습니다.

- 이번 수정 검증: 타입 검사·린트·빌드, 단위 테스트 13개, 접수·관리자 업무 브라우저 테스트 6개 통과. 모바일 크기 테스트에서는 `randomUUID`를 비활성화해 접수·응답 유실 재시도·재접수·엑셀 출력을 검증했습니다. 격리 DB를 사용했으며 실제 Supabase에 테스트 주문을 추가하지 않았습니다.

### 검증 결과와 한계

- 타입 검사·린트·프로덕션 빌드 통과.
- 단위 테스트 12개: 할인 짝·혼합·상한·배송지 분리, 기존 입력/날짜/재고 규칙, 요청 출처·DB 오류 분류, 실제 생성 XLSX의 열 순서·수량·전화번호/우편번호 앞자리 0·수식이 아닌 문자열 확인.
- PGlite(Postgres) 통합 5개: 실제 마이그레이션, 주문 재시도, 실패 롤백, 가격 보존, 재고 음수·반환·설정 변경, 결제 후 취소 거절, 출력/발송 재시도, 재접수 원본 보존, RLS·함수 실행 권한, 날짜·검색·페이지 처리. 정렬 추가 테스트는 그룹 단위 순서·재시도·잘못된 목록 및 권한 차단·동시 편집 충돌·새 상품 배치·기존 재고와 정렬 보존을 검증합니다.
- 기존 주문 화면 Playwright 54개 통과(데스크톱·태블릿·휴대폰).
- 관리자·실제 접수 경로 Playwright 9개 통과(세 화면 크기). 로그인/접근 제한 → 상품·설정 저장 → 비회원 접수 → 카운터 결제 → XLSX 다운로드 → 발송 → 재접수 → 결제 전 취소를 검증했습니다. 접수 성공 응답을 의도적으로 끊은 뒤 같은 번호 복구·초안 제거도 확인했습니다. 저장소 차단 시 메모리 기반 접수·완료 번호 안내를 세 화면 크기에서 추가 확인했습니다. 상품·과일 그룹 드래그 정렬, 저장 전 취소, 저장·새로고침 후 유지와 일반·체험 분리를 확인했으며 모바일에서는 브라우저 터치 이벤트로 이동을 검증했습니다.
- 상품 입력 개선 후 관리자 시나리오를 데스크톱·태블릿·휴대폰에서 재검증했습니다(3개 통과). 2.5kg 등록·수정 시 중량 보존, 판매 중 기본값, 재고 입력 표시·숨김과 숨긴 조정값이 기존 재고를 변경하지 않는 동작을 확인했습니다.
- 관리자 데스크톱 배치 개선 후에도 세 화면 크기의 관리자 시나리오 3개가 통과했습니다. 상품 폼·설정·발송 관리의 화면 캡처로 크기와 배치를 확인했습니다.
- 테스트용 Auth/PostgREST 응답 서버는 운영 앱에 포함되지 않습니다. 앱은 임시 디렉터리에서 실행하고 업무 RPC는 실제 PGlite SQL로 처리했습니다. 이후 실제 Supabase의 읽기·접근 제한을 별도로 확인했으며, 개발 서버의 주문·로그인 페이지 200 응답과 미로그인 관리자 API 401 응답도 확인했습니다. 원격 비밀번호 로그인·주문 쓰기 전체 동작, 다중 DB 연결의 실제 동시 부하, 실제 태블릿 하드웨어·택배 프로그램 파일 가져오기는 아직 검증하지 않았습니다.
- 고객 카카오/태블릿 회원 인증과 회원 기능, 결제 후 취소·환불, 온라인 결제·송장 API는 이번 구현 범위가 아닙니다.

## 구현 선택과 제약

- 디자인: 종이색 배경, 녹색과 과일색 포인트. 사용자 승인 완료 디자인이 아니라 검토 가능한 첫 구현입니다.
- 상품 중량은 kg 표시용 정수 gram으로 저장합니다. 3kg/5kg로 허용값을 고정하지 않습니다.
- 초기 카탈로그 SQL에 사용자/관리자/주문 권한을 섣불리 추가하지 않았습니다.
- 실상품이 없을 때 가상 상품으로 대체하지 않습니다. 미리보기는 별도 opt-in 경로입니다.
- 마지막 접수 버튼은 실제 저장 API가 구현될 때까지 비활성화합니다.
- 회원·관리자 로그인은 준비 안내입니다. 태블릿을 비회원으로 자동 저장하는 우회 구현이 없습니다.
- 작성 중 입력은 로컬스토리지에 임시 저장합니다. 새로고침·페이지 재진입 시 단계와 미완성 입력을 복원하며 수동 초기화 시 현재 주문의 임시 저장도 제거합니다.
- 체험은 날짜 선택 없이 일반 배송 요청일을 채웁니다. 일반 상품은 기존 방식의 예약 날짜를 검증합니다.
- 카탈로그 SQL은 파일만 작성했으며 원격 DB에 적용하지 않았습니다. PostgreSQL 실행 및 RLS 통합 검증은 연결 후 수행해야 합니다.

## 미리보기 피드백 반영

사용자의 이번 피드백과 약관 방식 답변을 기준으로 다음을 반영했습니다.

- 640px 이상 화면의 단계 원을 28px에서 44px로 확대하고 숫자와 완료 아이콘도 키웠습니다.
- `PhoneInput`은 모든 보내는 분·받는 분 입력(통합 수정 포함)의 숫자 키패드를 공통 처리합니다. 최신 가독성 피드백에 따라 숫자 입력에는 하이픈을 표시하고 텍스트 대치의 공백·문자는 유지하며, `phoneSchema`에서 다음·수정 완료 시 숫자 외 문자 제거와 11자리 검증을 적용합니다.
- 동의 기본값은 모두 미선택입니다. 사용자가 선택한 ‘전체 동의 (선택 포함)’를 추가하고 개별 체크·부분 선택 상태와 연동합니다. 상품·이벤트 안내 설명은 기존 동의 상세의 이용 목적을 근거로 합니다.
- 보내는 사람과 같음을 선택하면 수령인 필드는 읽기 전용으로 유지하면서 회색 배경·테두리·잠금 아이콘과 해제 안내를 표시합니다.
- 우편번호 필드 클릭 또는 Enter·Space로 기존 주소 검색을 엽니다. 검색 후 상세주소로 포커스를 이동합니다.
- `OrderEdit`은 보내는 분과 모든 배송지를 한 페이지에 표시합니다. 각 수정 버튼은 해당 영역에 포커스를 주며, 저장 전 연락처·주소·상품·예약 날짜를 검증하고 완료 즉시 최종 확인으로 복귀합니다. 취소는 수정 전 값을 유지합니다. 입력 필드, 상품 선택, 날짜 선택은 단계형 입력과 공유합니다.
- 추가 배송지의 받는 분 단계에서 이전을 누르면 최종 확인으로 돌아옵니다. 구현 선택으로 미완성 입력을 별도 보관하고 ‘배송지 추가 이어쓰기’를 제공합니다. 미완성 배송지는 완료할 때까지 주문 요약·금액에 포함하지 않으며 수동 초기화 시 함께 비웁니다.
- 통합 수정의 참고 근거: 기존 `src/components/common/steps/CheckInfo/Edit/EditReceiver/EditReceiver.tsx`의 수령인·주소·상품·일정 수정 및 `EditSender/EditSender.tsx`의 수정 완료 후 확인 복귀. 새 화면은 사용자의 요청에 따라 보내는 분과 모든 배송지를 함께 수정하도록 확장했습니다.

## 애플 텍스트 대치 입력 보완

- 사용자 제보: `010`을 텍스트 대치로 확장할 때 실시간 공백·하이픈 제거와 충돌해 숫자가 중복되는 현상. 원래 `PhoneInput`의 `onChange`에서 `event.target.value`를 직접 변경하던 코드를 확인했습니다. 애플 기기의 실제 이벤트 순서까지 재현한 것은 아닙니다.
- 당시 입력·붙여넣기·포커스 해제 시 원문을 유지하도록 수정했습니다. 이후 최신 하이픈 표시 요청에 따라 숫자 입력의 화면 표시만 변경했습니다. 공통 `phoneSchema`에서 숫자만 추출한 후 11자리를 검증합니다. 단계의 ‘다음’과 통합 수정의 ‘수정 완료’가 성공하면 정리한 값을 주문 입력에 반영합니다. 다른 항목에 오류가 있어 진행하지 못하면 입력 원문은 그대로 유지합니다.
- 숫자 키패드와 기존 숫자 외 문자 제거 결과는 유지합니다. 중복된 긴 번호나 사용자 예시 `010-1234234-5678 `처럼 숫자 개수가 11자리가 아닌 값은 자동 절단하지 않고 오류로 안내합니다.
- 실제 주문 저장 API는 아직 미구현입니다. 이번 변경의 저장 시점은 브라우저 내 주문 입력 상태에 반영하는 시점입니다.
- 검증: 타입 검사·린트·단위 테스트 9개·프로덕션 빌드 통과. 데스크톱·태블릿·휴대폰의 관련 브라우저 테스트 총 9개 통과. 대치 입력 이벤트 모사, 공백·하이픈·특수 공백 정규화, 입력/포커스 해제/오류 시 원문 보존, 긴 번호 거절, 보내는 분·받는 분·통합 수정의 저장 결과를 확인했습니다. 애플 기기의 실제 텍스트 대치는 별도 기기 확인이 필요합니다.

## LAN 미리보기 HMR 연결 수정

- 사용자 제보와 재현: `0.0.0.0:3000` 서버를 `192.168.0.164` 주소로 열면 `/_next/hmr` WebSocket 연결이 실패하고 전체 동의 클릭 후에도 `aria-checked=false`로 남았습니다. 서버 로그에서 해당 IP와 `127.0.0.1`의 개발 리소스 요청이 차단되는 것을 확인했습니다.
- 근거: 설치된 Next.js의 `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/allowedDevOrigins.md`와 `server/lib/router-utils/block-cross-site-dev.js`. 수신 주소 `0.0.0.0` 설정만으로 실제 LAN 주소의 Origin이 허용되지는 않습니다.
- `next.config.ts`에서 현재 컴퓨터의 IPv4 주소와 `127.0.0.1`을 정확한 호스트 목록으로 등록했습니다. 모든 외부 호스트를 허용하는 와일드카드는 사용하지 않습니다. 개발 서버 재시작 시 현재 네트워크 주소를 다시 읽습니다.
- 체크박스 제품 로직은 변경하지 않았습니다. README에 LAN 미리보기 실행 및 IP 변경 시 재시작 방법을 추가했습니다.
- 검증: 타입 검사·린트·프로덕션 빌드 통과. 실제 LAN URL `http://192.168.0.164:3000`을 사용한 Chrome의 데스크톱·태블릿·휴대폰 크기 테스트 9개 통과. HMR 프레임 수신, WebSocket 오류와 페이지 실행 오류 없음, 전체·개별 동의, 다음 단계 이동, 여러 배송지·통합 수정 흐름을 확인했습니다. 실제 휴대폰 하드웨어 검증은 아닙니다.
- 개발 서버는 `0.0.0.0:3000`으로 계속 실행 중이며, 기존 브라우저 탭은 새로고침해야 합니다.


## 주문 임시 저장과 화면 내 주문 안내

사용자는 새로고침으로 인한 입력 유실 방지를 위해 로컬스토리지 저장·CSS 당겨서 새로고침 방지의 검토 및 적용을 요청했습니다. 주문 중 안내는 유용성을 유지하면서 페이지 이탈을 없애는 모달 방식으로 구현했습니다.

- 기존 참고 근거: `RootsAndFruitsDeliveryServiceClient/src/stores/orderPostData.ts`의 `atomWithStorage("orderPostAtom", ...)`, `src/styles/global.ts`의 `html, body { overscroll-behavior: none; }`. 기존 프로젝트는 수정하지 않았습니다.
- `src/features/orders/draft-storage.ts`: 버전과 구조를 검증하는 임시 저장소. 일반/체험 및 미리보기/실제 입력 키를 분리합니다. 상품 자체·가격·인증정보는 임시 저장에 포함하지 않습니다. 저장은 입력 변경 시 수행하며 저장소 차단·용량 오류·손상된 데이터는 화면에 안내하고 주문 입력은 계속 허용합니다.
- `use-draft-form.ts`: React Hook Form의 원문 변경을 관찰해 다음 버튼을 누르기 전에도 보존합니다. 휴대폰 공백·하이픈은 기존 애플 텍스트 대치 대응대로 유지하며 다음·수정 완료 검증 시에만 정규화합니다.
- 단계, 연락처, 주소, 동의, 보내는 사람과 같음 선택, 상품 수량, 일정, 미완성 추가 배송지, 통합 수정 초안을 저장합니다. 통합 수정 초안과 수정 전 주문을 분리해 새로고침 후에도 취소의 의미를 유지합니다.
- 수동 초기화는 이 주문의 키만 제거합니다. 다른 탭의 저장 변경과 브라우저 뒤로 가기 캐시 복원 시 저장소를 재확인해 이전 고객 입력이 되살아나는 것을 방지합니다. 작성 중인 초안의 자동 만료·타이머는 없습니다. 완료 후 메인 이동은 아래 최신 구현 기록을 따릅니다.
- 주문 화면에서만 `overscroll-behavior-y: none`을 html/body에 적용합니다. 가로 탐색과 일반 스크롤은 유지하며 홈 등에서는 해제됩니다. CSS는 보조 수단이며 실제 iOS/Android 제스처는 기기별 확인이 필요합니다.
- 헤더 안내는 기존 `OrderGuide`와 공통 안내 문구를 재사용하는 스크롤 가능한 Radix Dialog입니다. 닫기·Escape·포커스 복귀를 지원하고 고정 하단 버튼 위에 표시됩니다. 별도 안내 페이지도 같은 설명을 사용합니다. 휴대폰에서는 모달 본문만 스크롤하고 상단 닫기와 하단 계속 작성 버튼은 항상 보이도록 분리했습니다.
- 저장된 상품을 현재 카탈로그에서 찾을 수 없거나 금액을 안전하게 계산할 수 없으면 입력을 삭제하지 않고 복원 불가 안내와 명시적 초기화 경로를 제공합니다. 상품을 임의로 제거·교체하는 정책을 추가하지 않습니다.
- 한계: 로컬스토리지는 같은 브라우저·origin 단위입니다. localhost와 LAN IP, 다른 기기 사이에 공유되지 않습니다. 당시 실제 주문 접수 API·인증은 미구현 상태였습니다. 현재는 접수 성공 시 초안 정리와 회원 연결을 구현했으며, 로그인 계정 전환에 따른 초안 분리는 별도 정책 확인 항목입니다. 작성 중 가격·날짜가 바뀐 경우의 접수 정책은 기존 미확정 사항이며 이 변경에서 임의로 결정하지 않았습니다.

### 임시 저장 반영 후 검증

- 타입 검사·린트·단위 테스트 9개·프로덕션 빌드 통과.
- LAN 미리보기 주소에서 Playwright 전체 51개 통과. 모달 스크롤/고정 버튼 및 복원 불가 상품 처리 보완 후 관련 18개 추가·재검증 통과(데스크톱·태블릿·휴대폰).
- 다음 버튼 전 원문·동의·주소 복원, 상품 수량·예약 날짜 복원, 일반/체험 분리, 페이지 이탈 후 재진입, 추가 중 배송지, 통합 수정 복원과 취소, 초기화 후 다른 탭 반영·재진입 시 빈 입력, 다른 저장 키 유지, 손상·쓰기 차단, 존재하지 않는 상품의 비파괴 처리, 모달 닫기·포커스 복귀·주문 화면 CSS 범위를 확인했습니다.
- 휴대폰·태블릿 안내 모달 캡처를 확인했습니다. 실제 iOS/Android 기기의 당겨서 새로고침 제스처와 브라우저 저장소 삭제 동작까지 검증한 것은 아닙니다. 개발 서버는 기존 LAN 주소로 유지합니다.

## 관리자 직접 접속 주소 변경

- 고객 화면 하단의 관리자 링크를 제거하고 관리자 화면 경로를 `/namu-admin`으로 변경했습니다. 로그인·로그아웃 이동, 메뉴 링크, 세션 갱신 경로와 설정 안내를 함께 갱신했습니다.
- 기존 `/admin`, `/admin/login`, `/admin/orders`는 새 주소로 리디렉션하지 않고 404를 반환합니다. 관리자 API와 서버·DB 권한 검사는 유지합니다. 주소 변경은 인증을 대체하지 않습니다.
- 격리된 DB에서 데스크톱·태블릿·휴대폰의 직접 접속, 기존 경로 404, 공개 링크 제거, 로그인·로그아웃 및 관리자 업무 흐름 6개 브라우저 테스트가 통과했습니다. 린트와 Webpack 프로덕션 빌드도 통과했습니다. 실제 Supabase 데이터는 변경하지 않았습니다.

## 카카오·태블릿 회원 인증

- `/login`은 카카오 로그인만 제공하고 `/tablet-login`은 사전 발급 ID·비밀번호를 사용합니다. 비회원 주문은 유지합니다. 태블릿 로그인은 공개 메뉴에 노출하지 않습니다. 로그인 상태/로그아웃은 고객 로그인 화면에서 확인합니다.
- Supabase SSR의 PKCE 시작·코드 교환·세션 갱신을 연결했습니다. 콜백 복귀는 허용된 주문 경로로 제한하며, 브라우저가 사용한 Host·프로토콜을 보존해 localhost/LAN IP가 섞이지 않도록 했습니다. 공식 카카오 로그인 버튼 리소스를 사용합니다.
- `private.tablet_accounts`는 RLS와 비공개 스키마로 보호합니다. 고객 종류는 `auth.identities`의 Kakao 제공자 또는 서버 전용 태블릿 목록에서 판별하고 사용자 메타데이터의 역할을 신뢰하지 않습니다. 고객·태블릿은 기존 관리자 정책을 통과하지 못합니다.
- `submit_customer_checkout`은 기존 주문 함수를 같은 트랜잭션 안에서 호출하고 인증된 회원 ID·접수 구분을 저장합니다. 같은 요청이 다른 계정으로 재시도되면 거절합니다. 만료 세션을 비회원으로 자동 전환하지 않으며 인증 오류 시 미확정 요청 ID를 유지합니다. 관리자 상세에 접수 구분을 표시합니다.
- `npm run tablet:create`를 추가했습니다. 관리자와 태블릿 발급은 공통 숨김 비밀번호 입력 함수를 사용합니다. 실제 계정 발급은 사용자 터미널에서 수행하며 공개 회원가입 경로는 없습니다.
- 후속 범위: 개인 회원의 주문 내역·저장 배송지, 관리자 재접수의 회원 연결 정책. 공용 태블릿 내역/저장 배송지 미제공은 제안 상태이며 이 작업에서 해당 화면·조회 권한을 새로 열지 않았습니다.
- 검증: 단위 테스트 16개, PostgreSQL 통합 테스트 6개, 타입 검사·린트·Webpack 프로덕션 빌드 통과. 새 인증 시나리오 9개(3가지 × 데스크톱·태블릿·휴대폰), 응답 유실 후 401을 거쳐 같은 요청으로 복구하는 주문 시나리오 3개, 기존 관리자 업무 흐름 데스크톱 1개를 통과했습니다. 휴대폰 로그인 화면 캡처를 확인했습니다.
- 외부 연결의 한계: 자동화 OAuth 제공자는 PKCE 검증을 수행하는 모의 서버입니다. 실제 카카오 동의·Supabase OAuth 및 실제 태블릿 장치 검증은 아직이며 원격 DB·인증 계정·비밀 설정을 변경하지 않았습니다. 사용자가 수행할 순서는 [회원 인증 설정](customer-auth-setup.md)에 정리했습니다.

### 실제 카카오 요청의 KOE205 수정

- 사용자 테스트에서 설정하지 않은 `account_email,profile_image`를 요청한다는 KOE205 오류를 확인했습니다. Supabase의 `options.scopes`는 Kakao 기본 항목에 추가되므로, `queryParams.scope`로 `profile_nickname`만 지정하도록 수정했습니다. 이메일·사진 동의를 추가로 요구하지 않습니다.
- 로컬 로그인 API에서 생성한 URL을 실제 Supabase로 요청해 카카오로의 302 응답에 `scope=profile_nickname`만 포함되는 것을 확인했습니다. 인증 코드·토큰·키는 기록하지 않았으며 실제 사용자 로그인 완료는 별도 확인 대상입니다.
- 카카오 요청 범위 회귀 검증을 기존 로그인·주문 연결·관리자 접근 차단 브라우저 테스트에 추가했습니다. 데스크톱 해당 시나리오 1개, 타입 검사·린트가 통과했습니다.

## 전화번호 입력 하이픈 표시

- 최신 사용자 결정: 전화번호 입력의 가독성을 위해 하이픈을 자동 표시합니다. `PhoneInput`을 사용하는 보내는 분·받는 분·통합 수정과 ‘보내는 사람과 같아요’, 이전 단계 이동·임시 저장 복원에 동일하게 적용합니다.
- `src/components/forms/phone-input.tsx`에서 React Hook Form의 입력값을 받아 숫자 입력을 `010-1234-5678` 형태로 표시합니다. 중간 자리 수정 시 커서를 유지하고 하이픈 경계의 Backspace/Delete도 처리합니다. DOM 이벤트의 원문을 직접 덮어쓰지 않습니다.
- 텍스트 대치의 공백·문자, 조합 중 입력, 11자리를 초과하는 값은 보존합니다. 기존 `phoneSchema`의 제출 시 숫자 정규화·11자리 검증과 임시 저장 원문 보존은 유지합니다. 실제 애플 기기의 텍스트 대치는 이번에도 별도 확인이 필요합니다.
- 검증: 타입 검사·린트·단위 테스트 16개 통과. 기본 Turbopack 빌드는 로컬 포트 권한 오류로 완료하지 못했으며 `npm run build -- --webpack`은 통과했습니다.
- 해당 빌드의 가상 주문 화면에서 데스크톱·태블릿·휴대폰 관련 브라우저 테스트 15개 통과. 연속 숫자 입력, 중간 자리 교체·커서, 하이픈 경계 삭제, 조합 및 텍스트 대치 이벤트 모사, 긴 번호 검증, 정보 복사·통합 수정·새로고침 복원을 확인했습니다. 휴대폰·태블릿 화면 캡처도 확인했습니다. 테스트용 서버만 종료했으며 원격 DB에는 주문을 접수하지 않았습니다.

## 체험상품 항목 분리

- 사용자 확정: 체험상품은 구분(일반/체험)·내용·가격·판매 중 여부만 관리하며 과일·중량·재고 관리·묶음 할인을 사용하지 않습니다. 오픈 전 데이터 초기화는 추후 작업이며 이번에는 기존 주문 기록을 변경하지 않습니다.
- 관리자 등록·수정에서 체험 선택 시 해당 항목만 표시하고, 목록·정렬도 과일 그룹 없이 상품 내용 단위로 처리합니다. 일반상품의 과일 그룹·중량·재고·할인은 유지합니다. 체험의 내용은 상품 표시 이름이므로 빈 값은 검증합니다.
- `src/features/admin/schema.ts`의 검증과 `supabase/migrations/202610020001_experience_products.sql`의 제약으로 체험상품의 과일·중량·재고 관리·묶음 할인 사용을 제한합니다. 기존 상품 테이블과 상품 ID를 유지하며 체험의 과일·중량은 NULL로 저장합니다.
- 상품 선택·최종 확인·통합 수정·재접수·관리자 검색은 체험의 내용으로 상품을 표시합니다. 체험 할인 안내를 숨기고 가격 계산과 접수 SQL 모두 할인·재고 차감에서 제외합니다. 새로운 주문 항목의 중량은 NULL이며 엑셀에 쓰이는 상품명은 내용입니다.
- 기존 체험상품 카탈로그는 새 조건으로 전환하지만 이미 접수된 주문·배송·상품 항목은 UPDATE하지 않습니다. 과거 재고 잔량·차감 기록도 유지합니다. 기존 내용이 비어 있던 상품만 이전 과일·중량을 내용에 보존합니다.
- 원격 Supabase에는 아직 적용하지 않았습니다. [적용 안내](supabase-setup.md)의 신규 SQL을 기존 마이그레이션 다음에 실행해야 합니다. `.env.local`과 기존 참고 프로젝트는 변경하지 않았으며 데이터 초기화·커밋·푸시는 수행하지 않았습니다.
- 검증 결과: 타입 검사·린트, 단위 테스트 18개, PGlite DB 테스트 8개, Webpack 프로덕션 빌드 통과. 브라우저 검증은 관리자·인증 기존 시나리오 21개, 신규 체험상품 시나리오 3개, 관련 주문·복원 시나리오 18개를 세 화면 크기에서 통과했습니다(수정 후 해당 실패 시나리오 재검증 포함). 데스크톱·휴대폰 등록 폼과 휴대폰 체험 목록·고객 선택 화면 캡처를 확인했습니다.
- 신규 브라우저 테스트는 일반→체험 전환 시 숨겨진 값 제거, 빈 내용 검증, 체험 정렬 저장·복원, API의 재고 활성화 거절, 2개 주문의 할인 없는 합계, 실제 접수, 체험→일반 전환을 격리된 DB로 검증합니다. 기존 임시 저장 테스트의 미완성 전화번호 표시 기대값도 앞선 하이픈 변경에 맞게 갱신했습니다. 단위·DB 테스트는 환경의 tsx CLI 파이프 제한을 피하기 위해 `node --import tsx --test`로 동일 테스트 파일을 실행했습니다.


## 카운터 결제 방식 기록

- 사용자 확정: 결제 완료 시 카드·현금·입금·기타 중 하나를 선택합니다. 기타 입력창은 추가하지 않고 기존 메모를 활용합니다.
- `PaymentAction`은 미선택으로 열리는 확인창을 제공하며 React Hook Form·Zod로 필수 단일 선택을 검증합니다. 요청 중 중복 입력을 막고 오류 시 확인창에서 안내하며 다시 시도할 수 있습니다.
- `checkouts.payment_method`에 주문 단위로 저장합니다. API와 DB 모두 네 값만 허용하고, `change_checkout`의 주문 행 잠금 안에서 결제 상태·시각·방식을 함께 변경합니다. 기존 결제 건이나 반복 요청의 최초 값을 덮어쓰지 않습니다.
- 카운터·주문 관리·발송 목록 및 주문 상세에 방식을 표시합니다. 과거 결제 방식은 미기록으로 표시하고 추측해 채우지 않습니다. 접수 내용·재고·취소·발송 규칙은 변경하지 않습니다.
- 적용 파일: `supabase/migrations/202610020002_payment_method.sql`. 사용자가 원격 DB에서 쿼리를 실행했다고 알렸습니다. 원격 적용 결과와 실제 결제 저장은 직접 확인하지 않았습니다. [DB 적용 안내](supabase-setup.md)를 참고합니다. 데이터 초기화·커밋·푸시는 하지 않았습니다.
- 검증: 타입 검사·린트·Webpack 프로덕션 빌드 통과. 단위 18개와 PGlite DB 9개를 통과했습니다. 새 DB 시나리오는 네 방식 저장, 누락·잘못된 방식 거절, 기존 결제 보존, 반복 요청의 시각·방식·이력 유지, 취소 제한과 함수 접근 권한을 검증합니다.
- 브라우저 6개 통과: 신규 결제 시나리오와 기존 결제→엑셀→발송 시나리오를 각각 데스크톱·태블릿·휴대폰에서 검증했습니다. 미선택 오류, 단일 선택·키보드 조작, 다시 열 때 초기화, 기타 입력창 미제공, 저장 후 응답 유실·재시도, 새로고침 후 방식 표시, API 검증을 확인했습니다. 휴대폰·태블릿 결제 확인창 캡처도 확인했습니다. 격리된 테스트 DB를 사용했으며 실제 Supabase/POS 처리는 수행하지 않았습니다.


## 목록의 재접수 표시와 운영 메모

- 사용자 요청: 재접수 건을 메모 영역에서 식별하고 상세를 열지 않아도 목록에서 메모를 확인합니다.
- `OrderNotes`와 `ReorderNotice`로 카운터·주문 관리·발송 목록과 상세 메모 영역에 `재접수 · 원본 N번`을 표시합니다. 카운터·주문 관리에는 저장된 배송지별 메모를 배송지 번호·수령인과 함께 접수 순서로 표시합니다. 긴 메모는 줄바꿈합니다.
