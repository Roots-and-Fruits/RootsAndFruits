# RootsAndFruits 리뉴얼 요구사항

이 문서는 프로젝트 생성 전 대화에서 합의한 내용을 정리한 기준 문서다. 최신 사용자 결정으로 바뀐 내용만 유지하며, 제안 또는 세부 확인이 필요한 내용은 마지막 절에 분리한다. 파일명, 테이블명, 라우트명은 별도로 확정하지 않는 한 구현 시 정할 수 있다.

## 1. 목적과 범위

- 체험농장 현장에서 손님이 태블릿 또는 QR로 접속한 개인 휴대폰으로 택배 상품을 주문한다.
- 접수 후 결제주문번호를 카운터에 제시한다. 사장님이 사이트에서 상품·총액을 확인하고 별도 POS에 입력해 결제한다.
- 사장님은 2명이며, 하루 주문은 수십 건에서 많으면 수백 건이다.
- 현재 운영 중이지 않고 새로 시작한다. 기존 주문·고객 데이터는 이전하지 않는다.
- `RootsAndFruits/`에 새로 구성한다. 별도 Spring 서버를 운영하지 않고 Next.js와 Supabase를 사용한다.
- Supabase 프로젝트는 새로 준비하며, 웹 배포 대상은 Vercel이다.
- 디자인은 기존과 무관하게 새로 설계한다. 기본 UI 라이브러리와 재사용 가능한 컴포넌트를 사용한다.
- 명시적으로 변경한 사항 외에는 기존 프로젝트의 업무 흐름을 기준으로 한다. 기존 소스 구조나 명칭의 복제는 요구하지 않는다.

## 2. 계정과 접근

### 고객 회원과 비회원

- 개인 고객은 카카오 로그인 또는 비회원 주문을 이용한다.
- 개인 회원 기능은 자신의 주문 내역·배송 상태 조회와 배송지 저장이다.
- 고객의 접수 후 주문 내용 수정·취소 기능은 제공하지 않는다.
- 비회원의 별도 주문 조회는 제공하지 않는다. 접수 완료 시 번호를 안내하고 이후 문의는 카운터에서 처리한다.

### 현장 태블릿 회원

- 태블릿은 같은 회원 인증 체계의 전용 계정으로 미리 로그인해 놓는다. 별도 기기 인증 시스템을 만드는 요구가 아니다.
- 이 주문은 전용 회원 계정에 연결되는 회원 주문이다. 손님은 로그인 절차 없이 로그인된 기기로 주문한다.
- 주문에 연결되는 회원과 손님이 입력하는 보내는 사람 정보는 별개다. 회원 프로필로 보내는 사람을 덮어쓰지 않는다.
- 개인 휴대폰 회원 주문과 태블릿 주문은 같은 주문 화면과 동작을 사용한다.
- 현장 태블릿에서 접수됐는지 구분할 수 있도록 전용 계정 식별 정보를 남긴다. 구체적인 필드명은 구현 시 결정한다.
- 태블릿 회원은 관리자 계정이 아니며 카운터·관리자 기능에 접근할 수 없다.

### 관리자

- 사장님용 관리자 계정 2개만 카운터와 관리자 페이지에 접근한다.
- 관리자 로그인은 고객 카카오 로그인과 구분된 ID·비밀번호 로그인이다. 관리자에게 카카오 가입을 요구하지 않는다.
- 로그인 화면을 분리하는 것에 그치지 않고 서버 및 DB 접근 권한도 분리한다.
- 관리자 계정을 사전에 준비한다. 고객의 카카오 로그인이나 일반 회원가입으로 관리자 권한을 얻을 수 없어야 한다.

## 3. 결제주문과 배송주문

```text
결제주문 1건: 계속 증가하는 결제주문번호, 주문자, 합산 금액, 결제 상태
  ├─ 배송주문 A: 수령인·주소·배송 일정·발송 상태
  │    └─ 상품 항목: 상품·단가·수량
  └─ 배송주문 B: 수령인·주소·배송 일정·발송 상태
       └─ 상품 항목: 상품·단가·수량
```

- 한 사람이 여러 배송지로 서로 다른 상품을 보낼 수 있다.
- 고객이 카운터에 제시하고 한 번에 결제하는 번호는 하나다.
- 배송지별 주문은 별도로 저장하고 배송·엑셀 작업에서 개별적으로 처리한다.
- 결제주문번호는 날짜마다 초기화하지 않고 계속 증가한다.
- 저장 배송지나 상품 정보를 수정하더라도 이미 접수한 주문의 주소·상품·단가는 유지한다.

## 4. 고객 주문 흐름과 초기화

```text
일반 / 체험 진입
→ 보내는 사람 입력
→ 받는 사람·주소 입력
→ 해당 배송지의 상품·수량 선택
→ 배송 일정 처리(일반/체험의 기존 차이 유지)
→ 다른 배송지 추가 시 받는 사람 입력부터 반복
→ 전체 주문 확인
→ 접수
→ 결제주문번호·총액·카운터 결제 안내
```

- 접수 전 입력 내용은 수정할 수 있다. 이전 단계로 돌아가면 작성 내용을 유지한다.
- 새로고침·화면 이탈로 작성 내용이 사라지지 않도록 브라우저 로컬스토리지에 임시 저장하고 재진입 시 복원한다. 다음 버튼을 누르기 전의 미완성 입력, 현재 단계, 추가 중인 배송지와 통합 수정 중인 내용도 포함한다. 전화번호 원문은 임시 저장 과정에서 정리하지 않는다.
- 주문 화면은 CSS로 세로 방향 당겨서 새로고침을 억제한다. 브라우저별 지원 차이가 있으므로 입력 보존은 임시 저장·복원으로 처리하고, 일반 스크롤은 유지한다. 저장소 사용이 차단되면 사용자에게 안내한다.
- 주문 중 헤더의 주문 안내는 화면을 이동하지 않는 모달로 제공한다. 닫으면 작성하던 입력과 단계로 돌아온다. 홈의 주문 안내 페이지는 유지한다.
- 임시 저장에 시간에 따른 자동 초기화를 추가하지 않는다. ‘처음부터’ 초기화는 현재 주문의 임시 저장·수정 중 내용·추가 중 배송지를 함께 지우고 로그인 데이터는 유지한다. 공용 기기 안내를 제공한다.
- 최종 확인의 수정 버튼은 단계형 입력으로 되돌아가지 않고 별도의 통합 수정 화면을 연다. 보내는 분과 모든 배송지의 수령인·주소·상품·배송 일정을 한 페이지에서 수정하고, 수정 완료 시 최종 확인으로 바로 돌아온다. 체험은 기존처럼 날짜 선택을 제공하지 않는다.
- 최종 확인에서 배송지를 추가한 뒤 받는 사람 단계의 이전 버튼을 누르면 최종 확인으로 돌아간다.
- 보내는 분과 받는 분의 휴대폰은 애플 텍스트 대치와 충돌하지 않도록 입력·붙여넣기·포커스 해제 시 원문을 유지한다. 숫자 키패드는 유지하며, 다음 단계 또는 수정 완료 시 공백·하이픈 등 숫자 외 문자를 제거한 결과를 11자리로 검증하고 주문 입력에 반영한다. 자릿수가 맞지 않는 번호를 임의로 자르지 않는다.
- 받는 분의 ‘보내는 사람과 같아요’ 선택 시 자동 입력된 필드가 수정 불가 상태임을 배경·테두리·안내 문구로 명확하게 표시한다.
- 주소 검색 버튼과 우편번호 필드 모두 검색창을 연다. 우편번호 필드는 키보드 Enter·Space도 지원한다.
- 휴대폰 등 좁은 화면에서는 상단의 현재 단계·전체 단계 수와 얇은 진행 막대로 입력 영역의 공간을 확보한다. 태블릿 등 넓은 화면에서는 확대된 단계 원과 숫자를 유지한다.
- 주문 화면의 이전·다음 버튼은 화면 크기 및 스크롤 위치와 관계없이 화면 하단에 고정한다. 버튼 영역 때문에 마지막 내용과 입력 요소가 가려지지 않도록 여백을 확보한다. 통합 수정의 취소·수정 완료에도 같은 고정 영역을 적용한다.
- 개인정보 필수 동의와 마케팅 선택 동의는 모두 미선택으로 시작한다. ‘전체 동의 (선택 포함)’와 개별 체크를 함께 제공하며 서로 상태를 연동한다. 선택 동의를 거절해도 주문할 수 있다. 이는 미리보기 피드백에 대한 사용자의 명시적 선택이다.
- 일반 상품과 체험 상품은 고객이 혼동하지 않도록 별도 목록과 진입 흐름으로 유지한다.
- 일반 전용 링크는 일반, 체험 전용 링크는 체험으로 시작한다. 공통 홈에서는 두 메뉴를 제공한다.
- 다음 주문 시작 시 해당 진입 화면으로 돌아간다.
- 입력 초기화와 다음 주문 시작은 버튼으로만 처리한다. 휴대폰·태블릿 모두 타이머를 사용하지 않는다.
- 초기화는 현재 주문 입력을 정리하며 회원 로그인은 유지한다. 실제로 접수한 주문을 삭제하는 동작이 아니다.
- 초기화 후 이전 고객의 입력 정보가 뒤로 가기나 남은 폼 상태로 복원되지 않도록 한다.

## 5. 상품 관리와 선택 화면

| 항목 | 요구사항 |
| --- | --- |
| 일반/체험 | 서로 구분해 관리하고 각 주문 흐름에 맞게 노출 |
| 과일 종류 | 감귤·한라봉 등 상품 이름에서 분리 |
| 중량 | 3kg·5kg 등 독립된 항목으로 관리 |
| 상품 내용 | 선물용·과일 크기 등 자유 입력 |
| 가격 | 원 단위, 배송비 포함 |
| 재고 관리 여부 | 상품별 설정, 기본은 미사용 |
| 재고 수량 | 재고 관리 시 판매 단위인 박스·개수로 관리 |

- 상품 선택 화면은 과일별로 묶은 목록이다. 각 상품의 중량·내용·가격과 수량 선택 버튼을 표시한다.
- 상품 사진과 사진 등록 기능은 이번 범위에서 제외한다.
- 수량은 `− / +` 방식으로 선택하며 해당 배송지의 상품 수량과 금액 합계를 확인한다.
- 배송지마다 직접 선택한다. 이전 배송지 상품 복사 버튼이나 자동 채움은 제공하지 않는다.
- 새 배송지의 상품 수량은 0부터 시작한다. 이미 작성한 배송지로 돌아가면 그 선택은 유지한다.
- 상품은 하나 이상 선택해야 다음 단계로 진행한다.
- 상품 판매 상태와 정렬 등 명시적으로 없애지 않은 기존 관리 기능은 기존 흐름을 참고한다.
- 과일 종류 목록 편집 방식, 중량 허용값 등 세부 입력 제약은 기존 사실과 사용 맥락을 확인해 정한다. 3kg·5kg만 허용한다고 단정하지 않는다.

## 6. 가격과 재고

### 금액

- 상품 가격에 배송비가 포함된다. 별도 배송비를 더하지 않는다.
- 묶음 배송 할인은 제외한다. 향후 추가될 수 있지만 현재 할인 기능을 구현하지 않는다.
- 각 배송주문의 금액은 상품 단가 × 수량의 합이며, 결제금액은 모든 배송주문의 합계다.
- 카운터의 상품 합산은 판매 상품의 식별자를 기준으로 한다. 과일이 같아도 중량·내용 등이 다른 상품은 구분한다.

### 재고

- 재고 미사용이 기본이다. 미사용 상품에는 재고 수량에 따른 판매 제한·차감을 적용하지 않는다.
- 사용 상품은 주문 접수 때 차감한다. 결제 완료 때 추가 차감하지 않는다.
- 선택 중 예약, 재고 선점, 예약 만료 타이머는 구현하지 않는다.
- 선택 시 주문 가능했던 상품은 접수 직전에 재고가 부족해져도 주문을 허용한다. 재고 50개에 51개·52개가 판매되는 정도의 초과 판매를 감수한다.
- 이미 품절인 상품의 새 선택은 제한하되, 앞서 선택한 상품을 최종 접수에서 일괄 거절하는 엄격한 재고 정책을 도입하지 않는다.
- 초과 판매 수량을 잃지 않도록 음수 잔량으로 기록하고 관리자에게 부족 수량을 보여주는 것을 설계 기본안으로 한다.
- 미결제 접수도 차감 상태를 유지하며 자동 취소하지 않는다. 관리자가 전체 취소하면 해당 주문에서 차감한 재고를 반환한다.
- 동시 요청으로 재고 변경이 유실되거나, 중복 요청으로 재고가 중복 차감·반환되지 않도록 한다.
- 발송 후 취소의 재고 반환, 재고 관리 설정 변경 중인 주문의 처리 등은 구현 시 별도로 확인한다.

## 7. 카운터와 결제 상태

```text
관리자 로그인
→ 주문번호 검색 / 최근 주문 선택
→ 상품별 합산 수량·총액 확인
→ 별도 POS에 입력하고 실제 결제
→ 사이트에 결제 완료 기록
```

- 온라인 PG 승인, 자동 POS 연동, 사이트에서의 자동 환불은 현재 범위가 아니다.
- 사이트의 결제 상태 변경이 실제 POS 승인·환불을 실행한다고 표시하지 않는다.
- 두 관리자가 같은 주문을 처리하거나 재시도해도 결제 기록의 효과가 중복되지 않도록 한다.
- 처리 상태와 시각, 처리 관리자를 추적할 수 있도록 구성한다.
- 기존 토스 송금 화면 이동·계좌 안내를 무조건 유지하거나 삭제한다고 가정하지 않는다. 현장 POS 결제가 확정된 기본 흐름이며 보조 안내의 유지 여부는 해당 화면 작업 때 확인한다.

## 8. 주문 불변성, 전체 취소, 재접수

- 접수된 주문의 보내는 사람, 받는 사람, 주소, 상품, 수량, 배송 일정 등을 고객이나 관리자가 직접 수정할 수 없다.
- 결제·취소·출력·발송 등 운영 상태 변경은 가능하다. 기존 운영 메모는 접수 내용과 분리해 기존 흐름을 확인한다.
- 취소는 결제주문 전체만 지원한다. 배송지별·상품별 부분 취소는 제공하지 않는다.
- 관리자 재접수는 결제주문 전체의 입력 내용을 복사한다. 일부 배송주문만 골라 복사하는 기능은 범위에 없다.
- 복사한 입력은 새로 접수하기 전 수정할 수 있다.
- 금액은 현재 상품 가격으로 계산한다. 이전 단가를 유지하거나 임의 단가를 입력하는 기능은 포함하지 않는다.
- 최종 재접수 시 새로운 결제주문번호와 배송주문들을 생성한다. 원본 주문은 유지한다.
- 재접수와 원본 취소는 독립이다. 원본 취소를 선행 조건으로 강제하거나 새 접수와 함께 자동 취소하지 않는다.
- 재접수 화면에 원본이 자동 취소되지 않는다는 사실을 안내한다.
- 원본 주문과 재접수 주문의 관계를 기록한다.
- 결제 완료·발송 완료 상태를 복사하지 않는다. 새 주문은 미결제·미발송 상태이며 최종 접수 때 재고를 처리한다.
- 판매 중지 상품, 지난 배송 날짜, 회원 연결 등 재접수의 예외는 아래 미확정 항목을 참고한다.

## 9. 배송 날짜: 기존 동작 유지

다음은 기존 소스에서 확인한 동작이다. 화면의 ‘배송’ 표현만 보고 발송일 또는 수령일로 단정하지 않는다.

| 구분 | 기존 요청 날짜 | 기존 서버 저장 |
| --- | --- | --- |
| 일반 상품의 일반 배송 | 오늘부터 2일 뒤 | 요청 날짜에서 하루 차감 |
| 일반 상품의 예약 배송 | 오늘부터 3일 뒤부터 관리자 설정 기간까지 선택, 일요일 제외 | 선택 날짜에서 하루 차감 |
| 체험 상품 | 별도 날짜 선택 없이 상품 단계에서 오늘부터 2일 뒤 설정 | 요청 날짜에서 하루 차감 |

- 예약 최대 범위는 서버 설정을 사용하며 기존 캘린더의 값 부재 시 기본값은 14일이다.
- 일요일 선택 금지는 예약 캘린더의 기존 규칙이다. 일반·체험 기본 날짜에도 자동 적용한다고 확대 해석하지 않는다.
- 새 저장 구조에서 요청 날짜와 관리자 처리 날짜를 구분하더라도 기존 계산 결과는 유지한다.
- 한국 현장 운영 기준으로 날짜를 처리한다. 날짜를 UTC 변환하면서 하루가 달라지지 않도록 검증한다.
- 관리자 날짜 범위 설정 기능을 유지한다.

## 10. 엑셀 출력과 발송 관리

- 택배사 API 직접 연동과 송장번호 업로드를 이번 범위에 추가하지 않는다. 엑셀 출력 후 기존 택배 프로그램에서 송장 업무를 처리한다.
- 결제주문 단위로 보는 카운터와 달리 배송 목록은 배송주문별로 처리한다.
- 단순 다운로드 버튼만 제공하지 않고, 어떤 배송주문들을 출력했는지 출력 묶음과 상태를 저장한다.
- 화면 흐름: 출력 대기 → 엑셀 출력됨·발송 대기 → 발송 완료.
- 결제 대기·취소 주문이 출고 대상으로 잘못 포함되지 않도록 한다.
- 출력 묶음에는 포함된 배송주문, 생성 시각, 생성 관리자, 파일을 식별할 정보를 보관한다.
- 출력 묶음을 확인하고 해당 주문들을 한 번에 발송 완료 처리할 수 있어야 한다.
- 이미 출력된 주문은 기본 출력 대기 목록에서 제외한다.
- 브라우저의 실제 저장 완료를 완전히 확인할 수 있다고 가정하지 않는다. ‘엑셀 출력됨’은 파일 생성 성공을 기준으로 기록하고 재다운로드 경로를 제공한다.
- 파일 생성 실패를 성공 상태로 기록하지 않는다.
- 기본안: 같은 묶음 재다운로드는 같은 파일을 제공하고 새로운 출고 대상을 중복 생성하지 않는다.
- 기본안: 묶음에서 개별 배송주문도 선택해 발송 처리할 수 있고, 취소된 주문은 발송 완료 대상에서 제외한다.
- 구체적인 택배 엑셀 열·정렬·값 형식은 기존 `OrderTable.tsx`의 출력 형식을 먼저 확인한다. 이전 묶음 배송 할인에 의존한 수량 계산은 그대로 옮기지 않는다.

## 11. 이번 범위에서 제외하는 기능

- 별도 Spring 백엔드 및 기존 데이터 이전.
- 고객 주문 내용 수정·취소, 관리자 접수 내용 직접 수정, 부분 취소.
- 비회원의 주문번호 기반 공개 주문 조회.
- 태블릿을 비회원 접수로 저장하는 별도 주문 시스템.
- 작성 중 자동 초기화, 완료 후 자동 복귀 등 모든 주문 화면 타이머.
- 재고 선택 시 예약, 예약 만료, 접수 시점 부족을 이유로 한 엄격한 재고 차단.
- 묶음 배송 할인, 별도 배송비, 상품 사진, 배송지 간 상품 복사와 자동 채움.
- 온라인 PG·POS 자동 연동, 택배사 송장 발급 API.
- 데이터 모델·명칭·UI를 기존 프로젝트와 동일하게 복제하는 제약.

## 12. 제안 또는 구현 직전 확인할 세부 사항

아래는 추가 기능 도입 지시가 아니다. 관련 구현에 도달했을 때 기존 코드와 사용자 의도를 확인하고 확정한다. 이 목록 때문에 독립적인 프로젝트 기반 작업을 중단하지 않는다.

- **공용 회원 계정의 주문 내역·저장 배송지:** 주문 흐름은 개인 회원과 동일하다. 여러 손님이 쓰는 전용 계정의 회원 페이지 노출·접근 범위는 개인정보가 섞이지 않도록 확인한다. 무단으로 태블릿 전용 주문 흐름을 만들거나 비회원으로 전환하지 않는다.
- **가격 변경 중인 입력:** 새 접수에서 선택 당시 가격과 최신 가격 중 어느 것을 적용하고 고객에게 어떻게 안내할지 확인한다. 재접수에 현재 가격을 적용한다는 결정과 혼동하지 않는다.
- **재접수 예외:** 판매 중지·삭제 상품, 품절 상태, 과거 배송 날짜, 원본 회원과 새 주문의 연결 정책을 확인한다. 기존 제안은 상품 교체·날짜 재확인이며 사용자 확정 정책으로 취급하지 않는다.
- **재고 설정 변경과 취소:** 재고 관리를 끄거나 켜는 중에 작성·접수·취소되는 주문, 이미 발송한 주문 취소의 재고 복구 방식을 확인한다. 실제 반품 확인 후 수동 조정은 제안 사항이다.
- **출력 후 취소:** 이미 생성된 파일에 취소 주문이 포함될 때 경고·재출력·발송 차단 방식을 확인한다. 같은 파일 재다운로드와 취소 반영 재출력을 혼동하지 않는다.
- **출력 형식:** 기존 송장 엑셀을 참고하되 새 상품 구분에 따른 상품명·박스 수, 택배 프로그램의 요구 열과 사업장 고정 정보를 검증한다.
- **외부 설정:** Supabase·카카오·Vercel·도메인·주소 검색 서비스 설정, 관리자 및 전용 회원 계정의 실제 ID와 발급 절차는 연동 단계에 준비한다. 비밀값을 이 문서에 적지 않는다.
- **디자인:** 기존과 무관한 새 시안이 필요하다. 라이브러리 선택을 최종 디자인 승인으로 간주하지 않는다.

## 13. 핵심 수용 시나리오

1. 일반·체험 각각 기존 순서로 접수하며, 보내는 사람 한 명과 여러 받는 사람을 입력할 수 있다.
2. 배송지마다 상품을 따로 담고, 배송주문은 나뉘지만 결제주문번호와 합산 결제는 하나다.
3. 개인 회원·태블릿 전용 회원은 같은 주문 기능을 사용하며 회원 ID가 올바르게 연결된다. 비회원만 회원 연결 없이 접수한다.
4. 고객과 태블릿 계정은 관리자 페이지와 관리자 데이터 처리에 접근하지 못한다.
5. 작성 중·완료 후 기다려도 자동 초기화되지 않는다. 수동 초기화는 입력값만 지우고 로그인은 유지한다.
6. 상품은 과일별 텍스트 목록이며 배송비·묶음 할인 없이 합계가 계산된다. 다음 배송지의 선택은 비어 있다.
7. 재고 미사용 상품은 재고 때문에 막히지 않는다. 사용 상품도 선택 이후 소진됐다면 접수되며 초과 판매가 기록된다.
8. 같은 접수 요청을 재시도해도 주문번호·주문·재고 효과가 중복되지 않는다.
9. 접수 내용은 고객·관리자 모두 직접 수정할 수 없다. 재접수는 전체를 복사하고 현재 가격으로 새 번호를 만들며 원본을 자동 취소하지 않는다.
10. 전체 취소만 제공하고 반복 취소로 재고가 중복 반환되지 않는다. 결제 상태 변경이 실제 POS 작업을 실행하지 않는다.
11. 일반·체험 날짜 처리와 예약 가능 범위는 기존 소스의 동작과 일치한다.
12. 엑셀 출력 묶음에서 포함 주문을 추적하고 묶음 발송 완료를 처리할 수 있다. 출력 실패·재다운로드가 중복 발송 대상을 만들지 않는다.
