# Supabase 개발 환경 준비

이 단계는 새 개발 프로젝트를 기준으로 합니다. 기존 프로젝트의 데이터는 옮기지 않습니다.

송장번호 업로드 추가 적용: 기존 마이그레이션이 적용되어 있다면
`supabase/migrations/202610050002_delivery_tracking.sql` 전체를 SQL Editor에서 실행합니다.
이 SQL은 배송지별 송장번호와 저장 요청 결과 테이블, 동시 변경 확인용 버전 및 관리자 함수를 추가합니다.
기존 주문·상품·출력 파일·주문번호·문자 내역은 삭제하거나 초기화하지 않습니다. SQL 실행 자체로 문자를 보내지 않습니다.
실행 후 발송관리를 새로고침하고 ‘송장번호 업로드’를 사용합니다. 식별자가 없는 이전 파일은 자동으로 연결되지 않으므로 새 접수 엑셀부터 사용합니다.

1. Supabase 대시보드에서 새 프로젝트를 생성합니다. 데이터베이스 비밀번호는 개인 비밀번호 관리자에 보관합니다.
2. SQL Editor에서 아래 파일을 순서대로 **각각 한 번만** 실행합니다. 이미 적용한 파일을 재실행하지 않습니다.
   - `supabase/migrations/202609200001_catalog.sql`
   - `supabase/migrations/202609260001_operations.sql`
   - `supabase/migrations/202609260002_product_order.sql`
   - `supabase/migrations/202609290001_customer_auth.sql`
   - `supabase/migrations/202610020001_experience_products.sql`
   - `supabase/migrations/202610020002_payment_method.sql`
   - `supabase/migrations/202610030001_order_notifications.sql`
   - `supabase/migrations/202610030002_cancel_before_export.sql`
   - `supabase/migrations/202610050001_shipping_worklist.sql`
   - `supabase/migrations/202610050002_delivery_tracking.sql`
3. 프로젝트 URL과 API Keys의 Publishable key·Secret key를 `.env.local`에 추가합니다. 기존 미리보기 설정은 덮어쓰지 않습니다.

   ```dotenv
   NEXT_PUBLIC_SUPABASE_URL=프로젝트_URL
   NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=공개키
   SUPABASE_SECRET_KEY=서버_비밀키
   ```

4. 관리자 계정을 터미널에서 두 번 발급합니다.

   ```sh
   npm run admin:create
   ```

   각 실행에서 관리자 번호 1 또는 2, 아이디, 비밀번호를 입력합니다. 비밀번호는 화면에 표시하지 않습니다. 계정은 Supabase Auth에 생성하며 ID 매핑은 `private.staff`에 저장합니다. Auth 내부 이메일은 아이디 기반의 발송 불가 주소이고 실제 이메일·카카오 가입은 필요하지 않습니다. 기존 번호의 계정을 덮어쓰지 않습니다. 스크립트 실패 시 방금 생성한 인증 계정만 정리합니다.

5. 개발 서버를 재시작한 뒤 `/namu-admin/login`에서 로그인합니다.
6. 설정에서 송장 발송지 주소·우편번호, 예약 최대 기간, 공통 할인 금액을 입력합니다. 상품을 등록하고 판매 상태를 켭니다. 기본 재고 관리·할인 대상은 꺼짐입니다.
7. `/product`에서 테스트 주문을 접수합니다. 접수 상태와 결제 완료 상태에서 각각 엑셀 출력 전 취소/재고 반환을 확인합니다. 새 주문 → 결제 기록 → 엑셀 다운로드 → 취소 차단 → 발송 완료도 확인합니다. 사이트 상태 변경은 실제 POS 처리를 실행하지 않습니다.

## 권한과 운영 범위

### 기존 개발 DB에 상품 정렬 기능 추가

앞의 두 마이그레이션을 이미 적용했다면 SQL Editor에서 `supabase/migrations/202609260002_product_order.sql`만 한 번 실행합니다. 기존 파일은 재실행하지 않습니다. 이 파일은 기존 상품을 과일 그룹별로 정리하고 순서 저장 함수·새 상품의 자동 마지막 배치를 추가합니다. 상품·주문을 삭제하지 않으며 이미 접수된 주문 정보도 변경하지 않습니다.

적용 후 관리자 상품·재고에서 일반상품은 그룹·상품을, 체험상품은 상품만 손잡이로 이동한 뒤 ‘순서 저장’을 누릅니다. 일반상품은 기존 과일 그룹 마지막 또는 새 그룹으로 추가되며, 체험상품은 목록 마지막에 추가됩니다. ‘순서 취소’로 아직 저장하지 않은 이동을 되돌릴 수 있습니다.

### 접근 권한

- 비회원은 공개 상품·배송 설정만 조회할 수 있습니다. 주문 조회·생성 RPC를 직접 호출할 권한은 없으며 비회원 접수는 서버 검증을 거칩니다.
- 관리자 페이지·API는 실제 인증 사용자와 관리자 매핑을 확인합니다. DB 쓰기 함수는 서버 비밀 키로만 호출하며 관리자 작업마다 등록된 관리자도 확인합니다.
- 원격 Auth의 로그인 제한·세션 갱신과 REST 응답은 이 실제 프로젝트에서 추가 확인해야 합니다. 로컬 테스트 서버가 이를 검증했다고 간주하지 않습니다.
- 고객·태블릿 회원 인증은 [회원 인증 설정](customer-auth-setup.md)을 따릅니다. 전용 회원을 비회원으로 바꾸는 임시 구현은 없습니다.
- 비밀번호 초기화는 현재 Supabase의 관리자 기능으로 처리합니다. 고객용 공개 가입·관리자 자체 가입·임의 권한 부여 UI는 제공하지 않습니다.

실제 계정·키·개인정보가 포함된 주문을 문서·대화·테스트 자료에 복사하지 않습니다.

카카오 고객 로그인과 태블릿 계정은 [회원 인증 설정](customer-auth-setup.md)을 따릅니다. 추가 SQL 적용 후 앱을 업데이트합니다.


### 기존 개발 DB에 체험상품 간소화 적용

기존 네 개 마이그레이션을 적용했다면 [202610020001_experience_products.sql](../supabase/migrations/202610020001_experience_products.sql) 전체를 SQL Editor에서 한 번 실행한 뒤 앱을 업데이트합니다. 새 DB에는 위 목록 전체를 순서대로 적용합니다.

- 기존 체험상품의 과일·중량을 비우고 재고 관리·묶음 할인을 끕니다. 내용이 비어 있던 상품은 이전 과일·중량을 내용에 보존합니다. 상품 ID·가격·판매 상태는 유지합니다.
- 이미 접수된 주문의 상품명·가격·중량·할인·재고 차감 기록은 수정하지 않습니다. 오픈 전 데이터 초기화는 이 SQL에 포함하지 않습니다.
- 체험상품의 저장·정렬·접수 규칙을 함께 변경하므로 화면 코드와 SQL을 모두 적용해야 합니다. 적용 후 체험상품 등록·수정, 과일 그룹 없는 순서 변경, 할인·재고 차감 없는 주문 접수를 확인합니다.

등록 시 400과 ‘데이터를 처리하지 못했습니다’가 나오고 기존 체험상품 수정도 멈춘다면, 이 마이그레이션 누락 여부를 확인합니다. 결제 방식·문자 SQL을 적용했더라도 체험상품 SQL이 자동 적용되지는 않습니다. 누락된 경우 위 파일 전체를 한 번 실행합니다. 주문 초기화용 `supabase/maintenance/20261003_reset_test_orders.sql`은 이 오류의 해결 쿼리가 아닙니다.

2026-10-03 사용자 요청에 따라 원격 SQL은 사용자가 직접 실행하며 에이전트가 Chrome에서 실행하지 않습니다. 실행 후 아래 읽기 전용 쿼리에서 모두 `YES`, `true`인지 확인할 수 있습니다. 주문번호·기존 주문·가격·판매 상태는 변경하지 않습니다.

```sql
select table_name, column_name, is_nullable
from information_schema.columns
where table_schema = 'public'
  and ((table_name = 'products' and column_name in ('fruit_type', 'weight_grams'))
    or (table_name = 'order_items' and column_name = 'weight_grams'))
order by table_name, column_name;

select exists (
  select 1 from pg_constraint
  where conrelid = 'public.products'::regclass
    and conname = 'products_category_fields'
) as experience_constraint_applied;
```

기존 체험 주문의 ‘택배 1kg · 체험귤’ 같은 상품명은 저장된 주문 내용에서 이전 접두어만 숨겨 표시합니다. 신규 주문은 변경된 DB 접수 함수가 ‘체험귤’만 저장합니다. 이미 생성한 엑셀 묶음의 재다운로드는 저장 파일을 그대로 반환합니다.


### 결제 방식 기록 추가

앞선 마이그레이션을 적용한 DB에서는 `supabase/migrations/202610020002_payment_method.sql`을 SQL Editor에서 한 번 실행합니다. 새 코드의 결제·취소 처리는 변경된 함수 인자를 사용하므로 앱 사용 전에 이 SQL을 적용해야 합니다.

결제주문에 `payment_method`를 추가하고 `change_checkout` 함수를 교체합니다. 카드(`card`)·현금(`cash`)·입금(`transfer`)·기타(`other`) 중 하나가 있어야 새 결제를 기록합니다. 상태·시각·방식은 한 트랜잭션으로 저장하며 반복 요청은 최초 기록을 유지합니다. 변경된 함수도 서버 전용 실행 권한과 관리자 검증을 적용합니다.

기존 주문을 삭제하거나 기존 결제 방식을 추정하지 않습니다. 기존 결제 건의 방식은 NULL(미기록)이며 취소·재접수·발송 규칙은 유지됩니다. 카운터에서 결제 완료 → 방식 선택 → 확인 후 목록·상세에 표시되는지 확인합니다. 기타 전용 입력창은 없으며 필요할 때 기존 배송지 메모를 이용합니다.

### 엑셀 출력 전 주문 취소 (결제 완료 포함)

앞선 SQL을 적용한 기존 DB에서는 [202610030002_cancel_before_export.sql](../supabase/migrations/202610030002_cancel_before_export.sql) 전체만 SQL Editor에서 한 번 실행한 뒤 앱을 배포합니다. 이전 SQL이나 주문 초기화 SQL을 다시 실행하지 않습니다. 원격 SQL은 사용자가 직접 실행합니다.

- 접수·결제 완료 여부와 관계없이 모든 배송지가 엑셀 출력 전인 주문만 관리자 전체 취소를 허용합니다. 한 곳이라도 출력/발송 상태이거나 출력 이력이 있으면 거절합니다.
- 기존 결제 방식·시각·금액·주문번호는 남기고 취소 상태·시각·관리자 이력을 기록합니다. 실제 차감된 재고만 한 번 반환하며 POS 결제 취소·환불은 사이트 밖에서 처리합니다.
- 취소와 출력 확정이 같은 주문을 먼저 잠그도록 두 DB 함수를 함께 교체합니다. 먼저 확정된 작업에 따라 뒤의 취소 또는 출력이 거절됩니다. 출력 파일을 만드는 도중 취소됐으면 해당 출력 묶음은 저장되지 않습니다.
- 기존 주문·상품·재고·주문번호 시퀀스를 초기화하거나 과거 주문을 취소하는 SQL이 아닙니다. 결제 방식의 상태 제약과 처리 함수만 갱신합니다.
- 적용 후 미결제/결제 완료 주문의 출력 전 취소, 재시도 시 재고 중복 반환 방지, 두 배송지 중 한 곳만 출력해도 취소 차단, 취소 건의 출력/발송 차단을 확인합니다. 문자 기능은 기존처럼 취소된 주문의 대기 알림을 전송 대상에서 제외하며 취소 안내 문자를 새로 발송하지 않습니다.


## 발송관리 작업 목록 업데이트

앞선 SQL을 적용한 기존 DB에서는 [202610050001_shipping_worklist.sql](../supabase/migrations/202610050001_shipping_worklist.sql) **전체를 SQL Editor에서 실행**한 뒤 발송관리 화면을 새로고침합니다. 이 파일만 추가로 적용하면 되며 이전 마이그레이션이나 주문 초기화 SQL은 다시 실행하지 않습니다.

- 결제 완료·미발송 작업을 모두 조회하는 관리자 전용 함수를 추가하고, 새 엑셀의 행 정렬을 출발 날짜 내림차순으로 맞춥니다.
- 테이블 구조·기존 주문·상품·금액·출발 날짜·주문번호는 변경하지 않습니다. 저장된 기존 엑셀 파일도 유지합니다.
- SQL 미적용 상태에서는 새 발송관리 화면에 DB 업데이트 안내가 표시됩니다. 원격 SQL은 사용자가 직접 실행합니다.
- 전체 적용 확인용 조회(데이터 변경 없음):

```sql
select to_regprocedure('public.list_shipping_work(uuid)') as shipping_work_function;
```

`list_shipping_work(uuid)`가 표시되면 조회 함수가 존재합니다. 실제 동작은 관리자 로그인 후 발송관리에서 확인합니다.
